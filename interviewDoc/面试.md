# 步骤一

> 我没有一开始把匹配逻辑塞入现有微服务，而是先建立了一个独立 matcher 命令。这样可以隔离 RabbitMQ、MongoDB 和网络抖动，保证算法正确性与性能结果可复现。  
>
> 代码上我先定义无行为的共享模型，把外部经纬度和内部米制坐标分离，也把业务订单 ID 和流水线 Sequence 分离。然后建立 Default、Parse、Validate 三层配置处理，用独立 FlagSet 避免测试间全局状态污染，并通过 errors.Join 一次报告多个准入错误。  
>
> 这一阶段刻意没有实现匹配算法，输出中明确标记 skeleton，避免把“程序能运行”和“业务已经完成”混淆。后续所有生成器、算法和 CSP 流水线都在这个稳定边界上逐步增加。

题目最终要求的是：

- 生成骑手和订单；
- 按距离匹配；
- 使用 goroutine、channel、CSP；
- 在 2 核、4GB 下压测；
- 输出订单最少的 10 名骑手。

但如果一开始直接接入 RabbitMQ、MongoDB、Kubernetes、OSRM 和现有微服务，会产生很多干扰变量。

先做一个独立的 `matcher` 命令，把算法问题从微服务集成问题中隔离出来

```
cmd/matcher           程序入口和模块装配
internal/config       配置解析及准入校验
internal/model        共享数据模型
internal/generator    数据生成
internal/matcher      匹配算法
internal/pipeline     CSP 并发编排
internal/report       统计报告
```

`main` 负责组装，不应该承载 KD-tree、统计等具体算法。

# 步骤二

> 第二步我实现了确定性数据生成器。输入仍然使用经纬度，但所有骑手和订单会通过同一个固定原点投影成米制二维坐标，这样暴力匹配和 KD-tree 可以共享完全一致的距离定义。  
>
> 为了保证 A/B 对照有效，我没有让骑手和订单共享一个随机流，而是从主种子派生独立的 riderSeed 和 orderSeed。这样修改骑手数量或生成逻辑不会改变订单序列。  
>
> 骑手因为需要构建空间索引，所以一次性保存在内存中；订单最高达到一千万笔，因此通过有状态 OrderStream 按需生成，不保存完整订单切片。生成器只计算 PlannedArrivalNs，不负责等待，后续由 CSP producer 负责 pacing、取消和 admission delay 测量。  
>
> 数据模型支持 uniform、hotspot、skewed 三种空间分布，以及 uniform-window、front-loaded-burst、unbounded 三种到达模型，分别用于标准验收、突发背压和纯吞吐测试。

- 确定性
- 独立随机流
- 可重放
- 局部米制投影
- 流式生成
- 计划时间与实际投递分离
- 多种压力分布

给算法提供可重复、可流式生成、能覆盖不同压力形态的测试输入，同时不能让测试数据本身先耗尽内存。

2.生成器定义在 [generator.go (line 40)](D:/Code/ride-sharing-main/ride-sharing/internal/generator/generator.go:40)

骑手一次性保存在切片中，因为后面的 KD-tree 必须基于完整骑手集合构建空间索引。

最大场景是 10 万名骑手，这个规模可以放进内存。真正不能一次性保存的是 1,000 万笔订单。

- 骑手 UID 从 `1` 开始，避免默认零值看起来像合法 UID；
- 经度纬度和投影坐标同时保存；
- 切片一次性按准确容量分配，避免扩容；
- `rand.Rand` 是方法内部局部对象，不与其他生成过程共享状态。

订单必须流式生成：

只保存：

- 当前生成到哪个 Sequence；
- 总订单数；
- 到达配置；
- 随机数生成器当前状态。

不保存 `[]Order`

调用：

```
order, ok, err := stream.Next()
```

时才生成一笔订单

完整程序仍然有有界 channel 和 batch 内存，但不会因为订单从 1 万增长到 1,000 万而保存全部订单。



OrderStream 不能直接并发调用。

其中包含可变字段：

```
nextSequence
random *rand.Rand
```

`rand.Rand` 也不是并发安全的。

但这不是缺陷，因为后续 CSP 流水线将 OrderStream 交给单一 producer goroutine。它属于“单一状态所有者”：

```
一个 producer 独占 OrderStream
多个 worker 从 channel 消费订单
```

这比给随机生成器加锁更简单，也更符合 CSP。



Next()只计算：

```
PlannedArrivalNs
```

但不等待那个时间。

- generator 负责决定订单计划什么时候到达；
- pipeline producer 负责真实等待、投递和测量延迟。

如果生成器自己 `Sleep()`：

- 单元测试会真的等待 30 秒、3 分钟甚至 10 分钟；
- 无法单独验证计划时间；
- 无法准确区分生成耗时、等待耗时和 channel 背压；
- 取消和 deadline 会更难统一处理。

后续 producer 可以比较：

```
实际入队时间 - PlannedArrivalNs
```

得到 admission delay。

如果 channel 已满，producer 会阻塞，这段额外延迟正是背压的证

# 步骤三

> 第三步我先实现了串行暴力匹配器。它对每笔订单扫描所有骑手，按照局部投影后的距离平方选择全局最近骑手，距离完全相同时选择 UID 更小的骑手。使用距离平方可以避免对每个候选执行开方，同时保持完全相同的大小关系。  
>
> 构造 Matcher 时我会验证骑手 UID 和坐标，并复制骑手切片形成静态快照，避免调用方在运行期间修改位置。Match 本身只读，不读取全局负载，也不依赖时间或随机数，所以同一输入一定得到同一结果。  
>
> 暴力版本的复杂度是每单 O(N)、整体 O(N×M)，不能支持十万骑手和一千万订单。它的目的不是跑最大规模，而是作为后续 KD-tree 的标准答案：两种算法在相同输入上逐单比较骑手 UID 和距离，从而验证优化没有改变业务语义。

串行暴力匹配器。先实现一个足够简单、容易人工验证的标准答案，再用它验证后续 KD-tree 和并发实现。
