# 步骤一

> 我没有一开始把匹配逻辑塞入现有微服务，而是先建立了一个独立 matcher 命令。这样可以隔离 RabbitMQ、MongoDB 和网络抖动，保证算法正确性与性能结果可复现。  
>
> 代码上我先定义无行为的共享模型，把外部经纬度和内部米制坐标分离，也把业务订单 ID 和流水线 Sequence 分离。然后建立 Default、Parse、Validate 三层配置处理，用独立 FlagSet 避免测试间全局状态污染，并通过 errors.Join 一次报告多个准入错误。  
>
> 这一阶段刻意没有实现匹配算法，输出中明确标记 skeleton，避免把“程序能运行”和“业务已经完成”混淆。后续所有生成器、算法和 CSP 流水线都在这个稳定边界上逐步增加。

题目最终要求的是：

- 生成骑手和订单；
- 按距离匹配；
- 使用 goroutine、channel、CSP；
- 在 2 核、4GB 下压测；
- 输出订单最少的 10 名骑手。

但如果一开始直接接入 RabbitMQ、MongoDB、Kubernetes、OSRM 和现有微服务，会产生很多干扰变量。

先做一个独立的 `matcher` 命令，把算法问题从微服务集成问题中隔离出来

```
cmd/matcher           程序入口和模块装配
internal/config       配置解析及准入校验
internal/model        共享数据模型
internal/generator    数据生成
internal/matcher      匹配算法
internal/pipeline     CSP 并发编排
internal/report       统计报告
```

`main` 负责组装，不应该承载 KD-tree、统计等具体算法。

## 代码文件

1.先看 [model.go (line 1)](D:/Code/ride-sharing-main/ride-sharing/internal/model/model.go:1)，因为模型定义了系统中信息的语义

`GeoPoint` 是系统边界模型，对接原项目的经纬度。

`Point2D` 是算法模型，单位是米，用于欧氏距离和 KD-tree。

> 我没有为了算法方便破坏原项目的经纬度模型，而是在 matcher 边界增加了适配层。外部保持业务语义，内部使用更适合空间索引的米制坐标。

2.第二份代码：config.go ：承担的是最小版 Admission Gate，也就是“非法任务不能进入流水线”

`algorithm` 回答“怎样查找候选骑手”； algorithm = kd-tree

`strategy` 回答“根据候选骑手怎样做最终分配”  strategy  = balanced

3.第三份代码：`cmd\matcher\main.go`

```
读取命令行参数
    ↓
解析并校验配置
    ↓
非法：打印错误并退出
    ↓
合法：打印最终生效配置
```

```
main.go
   ↓
pipeline.Run()  # 研究 pipeline代码
   ↓
真正 CSP 并发逻辑
```

4.对应测试位于 [config_test.go (line 11)](D:/Code/ride-sharing-main/ride-sharing/internal/config/config_test.go:11)

主要证明四件事：

1. 没有参数时，`Parse(nil)` 与 `Default()` 一致。
2. 命令行参数能够正确覆盖默认值。
3. 多个非法字段可以一次全部报告。
4. `nearest` 不允许混入策略 B 参数。
