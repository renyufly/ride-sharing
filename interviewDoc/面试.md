# 步骤二

> 第二步我实现了确定性数据生成器。输入仍然使用经纬度，但所有骑手和订单会通过同一个固定原点投影成米制二维坐标，这样暴力匹配和 KD-tree 可以共享完全一致的距离定义。  
>
> 为了保证 A/B 对照有效，我没有让骑手和订单共享一个随机流，而是从主种子派生独立的 riderSeed 和 orderSeed。这样修改骑手数量或生成逻辑不会改变订单序列。

> 数据模型支持 uniform、hotspot、skewed 三种空间分布，以及 uniform-window、front-loaded-burst、unbounded 三种到达模型，分别用于标准验收、突发背压和纯吞吐测试。

- 确定性
- 独立随机流
- 可重放
- 局部米制投影
- 流式生成
- 计划时间与实际投递分离
- 多种压力分布

给算法提供可重复、可流式生成、能覆盖不同压力形态的测试输入，同时不能让测试数据本身先耗尽内存。

# 步骤三

> 第三步我先实现了串行暴力匹配器。它对每笔订单扫描所有骑手，按照局部投影后的距离平方选择全局最近骑手，距离完全相同时选择 UID 更小的骑手。使用距离平方可以避免对每个候选执行开方，同时保持完全相同的大小关系。  
>
> 构造 Matcher 时我会验证骑手 UID 和坐标，并复制骑手切片形成静态快照，避免调用方在运行期间修改位置。Match 本身只读，不读取全局负载，也不依赖时间或随机数，所以同一输入一定得到同一结果。  
>
> 暴力版本的复杂度是每单 O(N)、整体 O(N×M)，不能支持十万骑手和一千万订单。它的目的不是跑最大规模，而是作为后续 KD-tree 的标准答案：两种算法在相同输入上逐单比较骑手 UID 和距离，从而验证优化没有改变业务语义。

串行暴力匹配器。先实现一个足够简单、容易人工验证的标准答案，再用它验证后续 KD-tree 和并发实现。

核心代码：internal\matcher\bruteforce\matcher.go

暴力算法每笔订单扫描所有骑手，逻辑足够直接：

```
当前最优 = 第一个骑手

依次检查其余骑手：
    如果距离更小：
        替换当前最优
    如果距离相同且 UID 更小：
        替换当前最优

返回当前最优
```

没有空间索引、树遍历和复杂剪枝，因此更适合作为 oracle，也就是标准答案

```
同一批骑手
同一批订单
       │
       ├── 暴力 Matcher
       └── KD-tree Matcher
                │
                ▼
       逐单比较 RiderUID 和距离
```


注意：

### 最大规模为什么不能使用暴力算法

最大规模：

```
100,000 riders × 10,000,000 orders
= 1,000,000,000,000
= 10¹² 次距离计算
```

即使每次比较很快，2 个 CPU 核也无法合理完成。

增加 goroutine 不能改变：

```
O(N × M)
```

而且在 2 核机器上创建大量 goroutine，只会增加调度和通信开销。

因此性能优化的优先级是：

```
先降低算法复杂度
再考虑有限并发
```

这正是步骤五引入 KD-tree 的原因



# 步骤四

> 第四步我增加了流式统计器。它不会保存全部 Assignment，而是每完成一笔分配就立即更新对应骑手的 `uint64` 计数、Assignment 总量和距离统计，因此内存与骑手数量相关，不随订单总量增长。  
>
> 所有骑手在初始化时就拥有计数槽，所以从未获得订单的骑手也会进入 Bottom 10。Bottom 10 使用容量为 10 的最大堆，堆顶保存当前候选中订单最多、UID 最大的最差候选，整体选择复杂度为 `O(N log 10)`。  
>
> 匹配阶段继续比较距离平方，只在最终骑手确定后执行一次开方。平均距离先四舍五入到微米并使用整数累计，保证后续并发合并时结果不受浮点加法顺序影响。P95 使用固定 50,001 桶的一米直方图，约占 400KB，不需要保存一千万个距离。  
>
> 最终通过生成数、Assignment 数和骑手计数总和进行计数守恒检查。不过数量守恒还不能完全排除“一单重复、一单遗漏”，所以后续并发流水线还会加入 Sequence 位图验证。

分配统计和 Bottom 10

前三步已经能回答：

> 这一笔订单应该分配给谁？

步骤四开始回答整场运行的问题：

- 一共成功分配了多少订单？
- 所有骑手的订单数之和是否等于订单数？
- 哪 10 名骑手订单最少？
- 有多少骑手一单都没有？
- 分配是否集中在少数骑手身上？
- 匹配距离是否因为策略变化而增大？



核心代码 是 `internal\report\report.go`

统计器必须流式处理，避免一千万笔订单意味着保存一千万个 Assignment。现在统计器收到一条最终 Assignment，就立即更新：

- 对应骑手计数；
- Assignment 总数；
- 距离总和；
- 最大距离；
- 距离直方图。

然后可以丢弃该 Assignment。

# 步骤五

> 第五步我在静态骑手集合上构建了二维平衡 KD-tree。树按 X、Y 轴交替切分，每层排序后取中位数，因此即使骑手坐标全部重复，树高仍保持在 O(log N)。节点保存在预分配的连续切片中，子节点使用整数下标，减少小对象和指针开销。  
>
> 每个节点还保存整棵子树的二维包围盒。查询时计算订单点到包围盒的最短距离，这个距离是子树中所有骑手距离的下界。只有下界严格大于当前最佳距离时才能剪枝；下界等于最佳距离时仍必须搜索，因为子树中可能存在等距但 UID 更小的骑手。  
>
> KD-tree 和暴力算法共享距离函数、输入校验和平局规则。测试中使用 uniform、hotspot、skewed 九种组合、重复坐标、城市边界和一万笔基础订单进行逐单对照，Assignment 完全一致。  
>
> 当前构建复杂度为 O(N log²N)，对于十万静态骑手只执行一次，可以接受。二维合理分布下查询通常访问远少于 N 个节点，但精确 KD-tree 的最坏查询仍可能退化到 O(N)，所以性能结论最终以压测数据为准。

暴力扫描：每笔订单检查全部 N 名骑手
KD-tree：利用空间结构跳过不可能包含更优结果的子树

业务语义完全不变：

- 仍然选择投影距离最小的骑手；
- 距离相同仍然选择 UID 更小者；
- 不是近似最近邻；

核心代码 `internal\matcher\kdtree\matcher.go`

KD-tree 会按坐标轴递归划分空间

理想情况下，KD-Tree 最近邻查询可以远少于 `O(N)` 的全量扫描

## 适合静态骑手，不适合直接更新移动位置

节点和包围盒在构建后不再修改，所以可以被多个 goroutine 无锁共享。

但如果骑手位置改变：

```
rider.Point 改变
```

相关节点和所有祖先的包围盒可能都要更新。直接修改骑手而不更新边界，会让剪枝不正确。

生产环境支持移动骑手时，可以考虑：

- 周期性构建新的只读 KD-tree 快照；
- 双缓冲切换新旧索引；
- 将频繁移动的骑手放入增量层；
- 使用更适合动态更新的空间结构；
- 按城市或网格分片



# 步骤六

> 第六步我在已经验证正确的 Matcher 外层加入有界 CSP 流水线。系统只有一个 Producer 和固定数量的 Worker，不会为每笔订单创建 goroutine。Producer 是 OrderStream 和输入 channel 的唯一所有者，多个 Worker 竞争消费同一个 batch channel，自然完成 fan-out，因此当前不需要额外 Dispatcher。  
>
> channel 和 buffer pool 都是有界的。系统预分配 `Q+W` 个 batch buffer，Producer 发送成功后将底层数组所有权交给 Worker，Worker 处理完成后才归还池。如果下游变慢，Producer 会阻塞在获取 buffer 或 channel send 上，背压最终传播到 OrderStream，内存不会随订单总量增长。  
>
> KD-tree 是构建后只读的，可以被 Worker 共享；每个 Worker 则独占骑手计数和距离直方图，热路径不需要全局锁。策略 A 不读取实时负载，所以订单被哪个 Worker 处理不会改变匹配结果。Worker 退出后，主 goroutine按固定顺序合并整数统计，因此虽然 Worker 工作量每次可能不同，最终报告仍然确定。  
>
> 正常路径由 Producer 关闭输入 channel，Worker 排空后退出，主 goroutine等待所有 Worker 并执行五项计数守恒。错误路径通过 context 全局取消；Worker panic 会记录订单 ID、Sequence、Worker ID 和堆栈，并让整次运行失败，不能吞掉订单后继续报告成功。

## 为什么不能每笔订单启动一个 goroutine

错误方案：

```
for 每笔订单 {
    go match(order)
}
```

一千万订单可能产生一千万个 goroutine。

即使 goroutine 初始栈较小，也会产生：

- 栈内存；
- goroutine 调度状态；
- 调度器开销；
- 大量短生命周期对象；
- 不受控制的在途任务；
- 下游跟不上时缺少背压。

而机器只有两个 CPU 核，同时真正执行 Go 代码的线程数量非常有限。

当前方案只创建：

```
1 个 Producer
W 个 Worker
```

订单量从一万增长到一千万，goroutine 数不会随之增长。

这叫固定 worker pool。

## 四、为什么不额外创建 Dispatcher

多个 Worker 直接消费同一个 channel：

```
batch, ok := <-batches
```

Go channel 的一次发送只会被一个接收者消费，不是广播。

因此多个 Worker 自然形成：

```
fan-out
```

谁空闲，谁就更早收到下一个 batch。

当前没有：

- 订单优先级；
- 指定 Worker 路由；
- 租户隔离；
- 特殊调度规则。

所以 channel 本身已经完成简单分发。额外创建 Dispatcher 只会增加一个 goroutine 和一次通信跳转。

如果未来出现优先级或路由规则，再引入独立 Dispatcher 才有价值。

> 文章确实要求生产级“优先级任务调度器”有 Dispatcher；但当前 Strategy A 只是一个 FIFO 式 bounded worker pipeline，`channel + workers 竞争消费` 本身就足以完成分发，因此没有必要为了架构形式再加一个空壳 Dispatcher

## 为什么每个 Worker 使用私有统计

如果所有 Worker 共享一个报告器：

```
globalCounts[riderIndex]++
```

就需要：

- mutex；
- 每次原子加；
- 分片锁；
- 或者其他同步机制。

热点订单可能集中到同一骑手，多个 Worker 会频繁竞争同一个计数位置。

当前设计是：

```
Worker 0：
    counts0[riderIndex]++

Worker 1：
    counts1[riderIndex]++
```

每个 Worker 只修改自己的：

- `[]uint64` 骑手计数；
- 距离直方图；
- Assignment 数；
- 距离总和。

所有 Worker 停止后，再执行：

```
global[i] =
    worker0[i] +
    worker1[i] +
    ...
```

热路径没有共享计数锁。

### 为什么策略 A 可以这样做

策略 A 的选择规则是：

```
只看订单位置和静态骑手位置
```

它不读取骑手当前累计订单数。

所以订单被哪个 Worker 处理，不会改变最终 Rider UID。

如果策略是：

```
优先选择当前订单数最少的骑手
```

那么 Worker 私有计数就不够，因为 Worker 0 看不到 Worker 1 刚刚增加的负载。这正是策略 B 需要单一 Coordinator 的原因。

### 私有统计的代价

内存从：

```
O(N)
```

变成：

```
O(W × N)
```

其中 W 是 Worker 数。

这是“用内存换锁竞争”的取舍。机器只有 2 核，因此默认 W=2，内存增长仍可控



## 有界 channel 如何形成背压

创建订单 channel：

```
batchChannel := make(
    chan *admittedBatch,
    options.ChannelCapacity,
)
```

假设：

```
batch-size       = 256
channel-capacity = 16
workers          = 2
```

队列最多缓存：

```
16 × 256 = 4096 笔订单
```

不会把一千万订单全部放进 channel。

### Worker 跟不上时发生什么

```
Worker 处理变慢
    ↓
batch channel 达到容量 Q
    ↓
Producer 发送 batch 阻塞
    ↓
Producer 停止调用 OrderStream.Next()
    ↓
上游生成速度被限制
```

这就是背压。

系统不会：

- 无限积累内存；
- 因队列满而丢弃合法订单；
- 继续从源读取并偷偷缓存。

它会让生产者等待消费者。



## 为什么还需要 batch buffer pool

只限制 channel 容量还不够。

如果 Producer 每次都创建：

```
make([]model.Order, 0, batchSize)
```

即使 channel 有界，整场一千万订单仍会不断产生短生命周期切片和 GC 压力。

所以创建了缓冲池：

```
bufferPool := make(
    chan *admittedBatch,
    channelCapacity+workers,
)
```

预先分配：

```
&admittedBatch{
    orders: make(
        []model.Order,
        0,
        batchSize,
    ),
}
```

总 buffer 数量为：

```
Q + W
```

其中：

- channel 最多持有 Q 个；
- Worker 最多各持有一个，共 W 个；
- Producer 需要新 buffer 时，如果全部正在使用，就等待回收。

核心在途容量大约是：

```
(Q + W) × B 笔订单
```

它与订单总量无关。

## 九、batch 的所有权如何转移

批次通过 slice 传递时，只复制 slice header，不复制底层订单数组。

如果 Producer 发送后立即重用：

```
batches <- batch
batch.orders = batch.orders[:0]
继续 append
```

Worker 和 Producer 会同时操作同一个底层数组，产生数据竞争和订单覆盖。

当前生命周期是：

```
buffer pool
    ↓ Producer 获取
Producer 独占并填充
    ↓ 发送成功
所有权转移给一个 Worker
    ↓ Worker 处理完成
Worker 将 buffer 归还 pool
    ↓
Producer 才可能再次获得并复用
```

Producer 发送成功后执行：

```
ownedBatch = nil
```

Worker 处理完成后：

```
recycleBatch(pool, ownedBatch)
ownedBatch = nil
```

这叫显式所有权转移。

## 十、为什么 pool 的回收是非阻塞发送

```
func recycleBatch(
    pool chan *admittedBatch,
    batch *admittedBatch,
) {
    select {
    case pool <- batch:
    default:
    }
}
```

正常情况下 pool 应该有空间。

但在取消或异常路径中，Producer 可能已经退出，不会再获取 buffer。如果 Worker 在 defer 中为了归还 buffer 永久阻塞，就可能导致 goroutine 泄漏，使 `Run()` 永远无法返回。

所以回收采用“尽力归还”：

- 能还就还；
- 异常关闭时 pool 满了就丢弃引用；
- 让 GC 回收；
- 绝不能为了复用 buffer 阻塞整个取消过程。

## 十一、Producer 的完整职责

Producer 位于 [pipeline.go (line 286)](D:/Code/ride-sharing-main/ride-sharing/internal/pipeline/pipeline.go:286)。

它负责：

1. 从 pool 获取空 batch；
2. 调用 `source.Next()`；
3. 等待每笔订单的计划到达时间；
4. 填满 batch；
5. 发送到有界 channel；
6. 统计 generated、admitted 和 admission delay；
7. 输入结束后发送最后一个不满 batch；
8. 最终关闭 batch channel。

### Generated 和 Admitted 有什么区别

`generated++` 发生在成功读取订单后：

```
order, ok, err := source.Next()
state.generated++
```

`admitted += batchSize` 发生在 batch 成功发送后：

```
case batches <- ownedBatch:
    state.admitted += uint64(batchSize)
```

所以取消时可能出现：

```
generated = 4
admitted  = 0
```

例如：

- Producer 已生成 4 笔订单；
- batch-size=8；
- batch 尚未填满；
- context deadline 到期；
- 4 笔订单没有进入 Worker 队列。

将两个阶段分开，可以准确说明订单停在哪里。



## 为什么默认 2 Workers

目标机器是 2 核，KD-tree 查询是 CPU 密集型任务。

默认：

```
GOMAXPROCS = 2
workers    = 2
```

可以让两个 Worker 并行执行查询。

Worker 太少：

```
CPU 可能利用不足
```

Worker 太多：

```
不会增加物理核心
增加调度切换
增加私有计数和直方图内存
可能破坏 cache 局部性
```

所以 2 是与资源约束一致的起点，不是任何机器上的绝对最优值

但它可能让热点附近的少数骑手获得大量订单，而其他骑手没有订单。

策略 B 研究另一个问题：

> 在不允许骑手距离无限增加的前提下，能不能适度牺牲距离，换取更均衡的订单分布？

它不是替代策略 A，而是显式可选扩展：

```
默认：
--strategy=nearest

显式启用：
--strategy=balanced
--top-k=8
--max-extra-distance=300
```



核心代码 `internal\pipeline\balanced.go`



## 单一 Coordinator 会不会成为瓶颈

它确实可能成为系统的串行瓶颈，因为每笔订单最终都要经过它。

但是否需要优化必须看数据。

最大 unbounded 场景中，策略 B 达到约：

```
301,384 单/秒
```

题目最高真实输入速率约：

```
16,667 单/秒
```

当前容量大约是目标的 18 倍，所以在本题约束下单 Coordinator 足够。

如果未来超过它，可以考虑：

- 按地理区域分片 Coordinator；
- 每个骑手只归属于一个分区；
- 按车型、城市或服务区拆分；
- 使用近似负载快照，接受一定非确定性；
- 将一致负载状态放入外部事务系统。

但不能简单增加多个 Coordinator，因为同一骑手的负载又会变成共享状态



## 策略 B 的性能结果怎样解释

> 策略 B 是策略 A 之外的显式负载感知扩展。它先通过 KD-tree 查询稳定排序的 Top-K 最近骑手，再限制候选距离不能超过最近距离加配置的额外米数，最后按当前负载、距离和 UID 依次选择。这样公平性改善始终受到候选数量和距离成本约束。  
>
> Top-K 查询只依赖静态位置，所以由多个 Candidate Worker 并行执行；但最终选择依赖实时全局负载，不能继续使用 Worker 私有计数。多个 Worker 即使使用原子计数，“读取—比较—选择—增加”仍不是原子的，而且结果会依赖调度顺序。因此我使用单一 Assignment Coordinator 独占全局负载。  
>
> Candidate Worker 的结果允许乱序完成，但 Coordinator 只按连续 Sequence 提交。重排内存通过固定数量的 CandidateResult envelope 控制在 `R=(Q+W)×B`，候选存储为 `O(RK)`，不会随订单总量增长。实现中还发现过一次大 batch 下的环形等待，最终通过 Producer 按 Sequence 预留 envelope，统一资源获取顺序解决。  
>
> 基础场景使用 TopK=8、额外距离 300m 时，CV 从约 0.576 降到 0.378，平均距离增加约 5.65%。这说明策略 B 改善了分配均衡，但付出了距离和吞吐成本，所以它没有取代默认的严格最近策略 A。



最大 unbounded 场景：

```
100,000 riders
10,000,000 orders
TopK=8
extra=300m
2 CPU / 4GiB
```

结果约：

```
Pipeline：33.18 秒
吞吐：301,384 单/秒
Peak Heap：29.96MiB
cgroup memory.peak：39.32MiB
重排峰值：1,853
重排上限：4,608
```

相比策略 A 的约 184 万单/秒，策略 B 明显更慢，原因是：

- KD-tree 不再只找 1 个，而是 Top-K；
- 每单维护容量 K 的候选堆；
- CandidateResult 经过额外 channel；
- 需要 Sequence 重排；
- Coordinator 串行选择并更新负载。

但它仍是题目最高真实速率的约 18 倍，所以在当前约束下容量足够。

真实十分钟窗口最大档：

```
全部 10,000,000 单完成
未完成 0
窗口后排空约 0.507ms
端到端 P99 约 1.311ms
重排峰值 18
```

说明真实计划速率下没有持续积压。
