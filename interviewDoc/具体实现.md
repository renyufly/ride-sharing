## 步骤一：建立独立程序骨架

### 本步目标与边界

本步建立一个与现有微服务解耦的 `matcher` 命令。它不连接 RabbitMQ、MongoDB、Kubernetes 或 OSRM，只负责读取、校验并打印运行配置。

本步骤完成时还**没有**生成骑手和订单，也**没有**执行暴力匹配、KD-tree 查询或 goroutine 流水线。当时的启动输出使用 `phase: "skeleton"` 和明确提示说明这一点，防止把程序“能启动”误认为算法已经完成；当前命令已经随步骤二演进为数据生成预览，见下一节。

### 具体实现过程

1. 新建 `cmd/matcher`，使算法练习可以用 `go run ./cmd/matcher` 单独启动，不受现有微服务基础设施影响。
2. 用独立的 `flag.FlagSet` 解析参数，而不是使用进程级全局 FlagSet。这样测试之间没有全局参数状态污染。
3. 配置包含骑手数、订单数、到达窗口、随机种子、算法、worker 数、batch 大小、channel 容量和匹配策略。
4. 第一版只允许 `nearest` 策略。`TopK` 与 `MaxExtraDistanceMeters` 字段已经在配置模型中保留，但必须为零，防止策略 A 完成前误启用策略 B。
5. 配置校验会一次收集并返回多个错误，例如骑手数为零且策略非法时，两项问题都能看到。
6. 将 `Order.ID` 与 `Order.Sequence` 分开建模：`ID` 用于业务幂等和追踪；`Sequence` 是单次运行中从零连续递增的顺序号，未来策略 B 可用它按序提交候选结果。
7. 对外位置使用 `GeoPoint{Latitude, Longitude}`；内部算法位置使用米制 `Point2D{X, Y}`。本步只冻结边界类型，坐标校验和投影属于步骤二。
8. 启动后以格式化 JSON 打印最终生效配置。到达窗口显示为 `30s`，避免 JSON 直接输出纳秒数造成误读。

## 步骤二：实现确定性数据生成器

### 本步目标与边界

本步实现确定性骑手生成、流式订单生成、三种到达模型、三种空间分布、经纬度校验以及局部米制投影。`matcher` 现在会生成全部配置数量的骑手和订单，但只保留前三条数据用于 JSON 预览。

本步仍然**不选择骑手、不累计订单数、不执行 KD-tree，也不启动 goroutine 或按真实时间等待**。订单只记录 `PlannedArrivalNs`；步骤六的 CSP 生产者才负责等待计划时间、向有界 channel 投递并测量 admission delay。

### 坐标模型与投影

测试城市边界框固定为：

```text
latitude:  37.70  ~ 37.82
longitude: -122.52 ~ -122.35
origin:     (37.76, -122.435)
earth R:    6,371,008.8 meters
```

该范围覆盖原项目的旧金山演示路线。所有骑手和订单共用边界框中心作为投影原点，并使用：

```text
x = R × (longitudeRadians - originLongitudeRadians) × cos(originLatitudeRadians)
y = R × (latitudeRadians  - originLatitudeRadians)
```

输入投影前必须满足纬度 `[-90, 90]`、经度 `[-180, 180]`，且两个值都不是 `NaN` 或正负无穷。边界框的四条边是包含关系。相同经纬度使用同一个投影器时会得到逐位相同的 `Point2D`。

### 可复现随机流

主种子默认是 `42`。生成器通过固定的 SplitMix64 finalizer 和不同的域常量派生 `riderSeed` 与 `orderSeed`。两个生成方法每次都从各自种子创建独立的 `rand.Rand`：

- 改变骑手数量或先后调用骑手生成，不会消费订单随机流。
- 相同主种子、边界框和参数重新创建 `OrderStream`，会从 `Sequence=0` 重放完全相同的业务 ID、位置和计划到达时间。
- 骑手 UID 从 `1` 连续递增；订单 `Sequence` 从 `0` 连续递增。
- 订单业务 ID 使用对 `orderSeed + Sequence` 的一一映射生成，和流水线排序字段分离且在单次数据集中不重复。

骑手一次性保存在切片中，因为空间索引需要完整骑手集合。订单由 `OrderStream.Next()` 每次构造一条；即使配置一千万订单，流对象本身也不保存一千万个订单。

### 到达模型

| 参数 | 行为 |
| --- | --- |
| `uniform-window` | 从 0 到完整窗口均匀安排，最后一单严格等于窗口末端 |
| `front-loaded-burst` | 约 80% 的订单安排在窗口前 20%，剩余订单分布在后 80% |
| `unbounded` | 所有 `PlannedArrivalNs` 都为 0，用于后续测纯吞吐 |

实现时曾由测试发现浮点换算导致 10 秒窗口的最后一单是 `9.999999999s`。现在对最后一个 Sequence 显式返回完整窗口，避免 1ns 的舍入误差。

### 空间数据分布

| 参数 | 用途 |
| --- | --- |
| `uniform` | 骑手或订单在整个边界框内均匀分布，作为标准验收数据 |
| `hotspot` | 85% 概率落在三个固定热点周围，其余保持均匀，用于订单热点测试 |
| `skewed` | 对归一化随机数做三次方变换，向边界框西南侧偏斜，用于骑手稀疏/倾斜测试 |

热点高斯采样可能越界，因此最终统一 clamp 到 `[0,1]` 后再映射进城市边界。测试会对三种分布逐点验证经纬度和投影结果。

## 步骤三：实现串行暴力匹配器

### 本步目标与边界

本步实现策略 A 的串行正确性基准：每来一笔订单，就扫描全部骑手，选择局部投影坐标中距离最近的骑手。该实现追求简单、确定和易于验证，后续 KD-tree 必须与它逐单对照。

本步只输出每笔订单的匹配结果以及生成数/匹配数，不累计每名骑手的订单数，不计算 Bottom 10、零订单人数、平均距离或 P95。这些属于步骤四。当前也没有 KD-tree、worker pool、channel 或真实到达时间等待。

### 新增和修改的代码

```text
internal/model/model.go                         新增通用 Assignment 结果模型
internal/matcher/bruteforce/matcher.go          串行暴力最近邻实现
internal/matcher/bruteforce/matcher_test.go     最近邻、平局、输入和规模测试
cmd/matcher/main.go                             逐单调用暴力匹配器并输出三条预览
```

### 具体实现过程

1. `bruteforce.New` 要求至少一名骑手，检查 UID 不重复，并拒绝含 `NaN` 或正负无穷的内部投影坐标。
2. 构造 Matcher 时复制骑手切片。测试期间骑手位置固定，复制后调用方不能在匹配过程中意外修改索引所依据的数据。
3. `Match` 只读取 `Order.Point` 与 `Rider.Point`，不读取原始经纬度，也不读取骑手历史订单数。
4. 距离比较使用：

```text
dx = order.Point.X - rider.Point.X
dy = order.Point.Y - rider.Point.Y
distanceSquared = dx × dx + dy × dy
```

只比较平方距离，不执行 `sqrt`。因为平方根在非负区间单调递增，距离平方最小的骑手就是实际距离最小的骑手，可以避免每个候选骑手一次不必要的开方。

5. 若 `candidateDistance < bestDistance`，替换当前最优骑手；若平方距离完全相等，仅当候选 UID 更小时替换。因此结果不依赖骑手切片顺序。
6. 返回的 `Assignment` 保留订单业务 ID、Sequence、骑手 UID 和平方距离。订单身份字段原样传递，方便后续检查遗漏、重复以及按序结果。
7. 主程序逐条读取 `OrderStream` 并立即匹配，不保存全部订单或分配结果；只保存前三条订单和 Assignment 用于演示。
8. 步骤三只支持实际执行 `brute-force`。配置层仍能识别未来的 `kd-tree` 枚举，但主程序会明确拒绝执行尚未实现的 KD-tree，避免静默回退或输出虚假结果。

### 正确性与复杂度

设骑手数为 `N`，订单数为 `M`：

- 单笔订单固定扫描 `N` 名骑手，时间复杂度为 `O(N)`。
- 全部订单时间复杂度为 `O(N × M)`。
- Matcher 持久保存静态骑手副本，构造期间临时使用 UID 集合检查重复，构建峰值空间复杂度为 `O(N)`；单次匹配额外空间为 `O(1)`。
- 主程序对订单保持流式处理，不因 `M` 增大而保存全部 Assignment。

这个版本不适合 `100,000 × 10,000,000`，因为需要约 `10^12` 次距离计算；它的价值是充当后续 KD-tree 的标准答案，而不是依靠更多 goroutine 掩盖算法复杂度。

### 本步测试数据与验证方式

| 用例 | 数据 | 验证点 |
| --- | --- | --- |
| 全局最近 | 3 名手工坐标骑手、1 笔订单 | 选择平方距离为 5 的骑手 |

## 步骤四：实现分配统计和最少 10 名输出

### 本步目标与边界

本步在串行暴力匹配器之后增加流式统计：累计每名骑手的订单数，输出订单最少的 10 名骑手，并计算零订单人数、订单数分布和匹配距离指标。

统计器每收到一条最终 Assignment 就立即更新状态，不保存全部 Assignment。当前仍然使用步骤三的串行暴力匹配器，不实现 KD-tree、并发 worker、到达等待或性能 profile。

### 新增和修改的代码

```text

internal/report/report_test.go   排序、零订单、统计公式、距离和异常输入测试
cmd/matcher/main.go              逐单 Observe，检查计数守恒并输出 report
```

### 流式累计与计数守恒

`report.New(riders)` 建立两项与订单总量无关的状态：

- `riderIndex map[UID]index`：把 Assignment 的骑手 UID 定位到计数槽。
- `riderCounts []RiderOrderCount`：为所有骑手保留计数，包括始终没有订单的骑手。

每条 Assignment 到达时：

1. 验证骑手 UID 存在。
2. 验证距离平方非负、不是 `NaN` 或正负无穷。
3. 对选中骑手的订单数加一。
4. 对最终距离平方执行一次 `sqrt`，更新距离总和、最大值和 P95 直方图。

正常结束后主程序强制检查：

```text
generatedOrderCount == assignmentCount
matchedOrderCount   == riderOrderCountSum
```

因为 `Observe` 每成功一次会同时增加 Assignment 总数和一个骑手计数，这两项再与生成数和匹配数交叉检查。步骤六还会加入 Sequence 位图，进一步证明没有重复或遗漏；本步骤尚未实现位图。

### Bottom 10 最大堆

最终扫描全部骑手计数，比较键固定为：

```text
(OrderCount ascending, RiderUID ascending)
```

扫描时只维护容量为 10 的最大堆。堆顶是当前保留候选中“最差”的一个，即订单数更大者优先；订单数相同时 UID 更大者更差。新骑手比堆顶更优时替换堆顶并恢复堆结构。

扫描完成后只对最多 10 个候选按 `(OrderCount, RiderUID)` 升序排列。若骑手不足 10 名则输出全部骑手。由于计数数组在初始化时包含所有骑手，零订单骑手自然参与比较，不会因从未出现于 Assignment 而丢失。

- 扫描时间复杂度：`O(N log 10)`。
- Bottom 10 选择额外空间：`O(10)`。
- 全部骑手计数和 UID 索引：`O(N)`，不随订单总量 `M` 增长。

### 骑手分配统计

完成后扫描骑手计数，计算：

```text
mean     = assignmentCount / riderCount
variance = Σ(countᵢ - mean)² / riderCount
stddev   = sqrt(variance)
CV       = stddev / mean
```

方差使用总体方差而不是样本方差，因为本次运行中的全部骑手就是被观测总体。没有订单时 `mean=0`，CV 明确定义为 0，避免除零或输出 `NaN`。

报告同时输出 `minOrders`、`maxOrders`、`zeroRiderCount`、`assignmentCount` 和 `riderOrderCountSum`。Bottom 10 与零订单数只描述纯就近策略产生的分布，不作为策略 A 失败条件。

### 固定内存距离统计

匹配候选比较仍然使用距离平方；只有胜出的骑手进入统计器后执行一次平方根。

- 平均距离：每个最终距离四舍五入到微米并使用 `uint64` 累加，结束时换算为米再除以 Assignment 数。微米误差对城市距离可以忽略，同时整数加法使并发 worker 以不同顺序合并时仍得到完全相同的平均值。
- 最大距离：保存精确的最大米制距离。
- P95：使用 `0~50,000m`、每桶 `1m` 的固定直方图，共 50,001 个 `uint64`，约 400KB，内存不随订单数增长。
- 距离落入 `ceil(distanceMeters)` 对应的桶，所以 P95 输出是所在 1 米桶的上界，误差小于 1 米。
- 超过 50km 的数据进入 overflow 计数。如果 P95 位于 overflow 区间，报告保守返回精确观测最大距离，并显式输出 `distanceHistogramOverflow`，不会静默伪造精度。

本题固定旧金山边界框的对角线小于 50km，正常生成数据不会进入 overflow；测试仍专门覆盖了该分支。

## 步骤五：实现 KD-tree 最近邻匹配器

### 本步目标与边界

本步为静态骑手集合建立二维平衡 KD-tree，并使用子树包围盒的距离下界剪枝。KD-tree 必须返回和步骤三暴力扫描完全相同的骑手 UID 与距离平方，包括等距时选择较小 UID。

主程序现在可通过 `--algorithm=brute-force` 或 `--algorithm=kd-tree` 选择串行算法。两种算法复用相同的生成器、投影坐标、距离函数、平局规则和统计器。本步仍未加入 goroutine、channel、批次或到达时间等待。

### 新增和修改的代码

```text

internal/matcher/bruteforce/matcher.go      改为调用共享规则，保持基准语义不变
internal/matcher/kdtree/matcher.go          静态平衡 KD-tree 构建与精确查询
internal/matcher/kdtree/matcher_test.go     逐单对照、边界、重复和退化场景测试
cmd/matcher/main.go                         根据 --algorithm 构造对应串行 Matcher
```

### 为什么抽取共享匹配规则

暴力扫描与 KD-tree 现在都调用：

```go
DistanceSquared(first, second Point2D)
IsBetter(candidateDistance, candidateUID, bestDistance, bestUID)
CopyAndValidateRiders(riders)
```

这样可以避免两个实现分别维护距离公式或平局逻辑。例如 KD-tree 若使用 `<=` 更新最佳骑手、暴力版本使用 `<`，重复坐标时就可能得到不同 UID。共享 `IsBetter` 固定为：距离更小，或者距离完全相同且 UID 更小。

### KD-tree 构建过程

1. 复制并校验骑手集合，拒绝空集合、重复 UID 和非有限投影坐标。
2. 深度为偶数时按 X 排序，奇数时按 Y 排序。
3. 主轴坐标相同后比较另一轴，两个坐标都相同后比较 UID，保证构建顺序确定。
4. 取排序后中位骑手作为当前节点，左右半区递归构建子树。
5. 每个节点保存自身骑手、左右子节点下标、切分轴，以及整棵子树的 `minX/maxX/minY/maxY`。
6. 所有节点保存在一个预分配的连续 slice 中，子节点用整数下标引用。构建后不再修改，因此后续可供并发只读共享。

中位数递归使树高约为 `O(log N)`，包括全部骑手坐标相同的退化输入。本实现为了代码清晰，在每一层对子切片排序，构建时间上界为 `O(N log²N)`；100,000 名静态骑手可以接受。若 profile 表明构建成为瓶颈，可改用线性选择算法把构建降到平均 `O(N log N)`，但不能以牺牲确定性为代价。

### 包围盒精确剪枝

对一个子树包围盒，先计算订单点到矩形的最短平方距离：

```text
dx = 0                         if minX <= x <= maxX
dx = minX - x                  if x < minX
dx = x - maxX                  if x > maxX

dy 同理
lowerBound² = dx² + dy²
```

如果下界严格大于当前最佳距离平方，子树中不可能存在更近骑手，可以安全剪枝。左右子树按下界较小者优先搜索，让最佳距离尽快收紧。

关键判断是：

```text
lowerBound² <= bestDistance² 时仍然搜索
```

不能用严格 `<`。当下界等于最佳距离时，子树中可能存在一个等距但 UID 更小的骑手；剪掉它会违反策略 A 的确定性平局规则。访问候选节点后仍统一使用共享 `IsBetter` 更新结果。

### 查询复杂度和适用边界

- 平衡构建后的典型二维最近邻查询会访问远少于 `N` 个节点。
- 查询额外栈空间通常为 `O(log N)`。
- 精确 KD-tree 在坐标分布不利或高维场景仍可能退化到 `O(N)`；本项目不预先承诺固定查询复杂度或吞吐量。
- 当前只有二维、静态、城市局部投影坐标，适合 KD-tree。动态骑手位置需要快照重建、增量索引或其他空间结构，不属于本步。

## 步骤六：为策略 A 加入有界 CSP 并发流水线

### 本步目标与边界

本步在已经验证正确的 Matcher 外层增加 CSP 流水线：一个订单生产者、一个有界批次 channel 和固定数量的 worker。每个 worker 共享只读 Matcher，但独占自己的骑手计数和距离统计，全部 worker 退出后再合并。

本步实现并发正确性、背压、取消、fatal panic 传播和正常排空。步骤七才会正式测量四档规模的峰值内存、CPU、GC 和 profile；本步骤不提前声称已经达到最终性能指标，也不实现策略 B。

```text
internal/pipeline/pipeline_test.go  守恒、背压、取消、panic、错误和计划到达测试
internal/report/report.go           Fork worker 私有状态、Merge 汇总、确定性距离总和

```

### CSP 结构与状态所有权

```text
OrderStream（唯一生产者）
        │
        ▼
有界 chan []Order（容量 Q 个 batch）
        │
        ├── Worker 0 ── 私有骑手计数、距离直方图、完成数
        ├── Worker 1 ── 私有骑手计数、距离直方图、完成数
        └── Worker W ── 私有骑手计数、距离直方图、完成数
                              │
                              ▼
                   worker 全部退出后按 ID 合并
```

- 只创建 `W` 个 worker goroutine 和一个生产者 goroutine，不为每笔订单创建 goroutine。
- 生产者是唯一关闭订单 channel 的角色。
- 多个 worker 竞争消费同一个 channel，自然完成 fan-out，不额外创建无业务价值的 Dispatcher goroutine。
- KD-tree 或暴力 Matcher 在构建后只读，可以安全共享。
- 报告器的 UID 到数组下标 map 只读共享；每个 worker 通过 `Fork()` 获得私有计数数组、距离直方图和累计值，热路径没有全局计数锁。
- worker 结束后把私有报告器交给调用方，此后不再修改；主 goroutine 按 worker ID 顺序 Merge。

策略 A 只依据订单位置和静态骑手位置，不读取累计负载，因此同一订单交给哪个 worker 不会改变被选中的骑手。`workerCompletedOrders` 会随调度变化，但最终骑手计数、Bottom 10、P95 和 Assignment 选择保持一致。

### 有界批次、缓冲池与背压

配置参数：

```text
workers          = W
batch-size       = B
channel-capacity = Q
```

订单 channel 最多容纳 `Q` 个批次。另预分配 `Q + W` 个容量为 `B` 的订单 slice：队列最多占有 Q 个，worker 最多各占有一个。生产者必须先从池中取得空 slice，填满或遇到输入结束后才发送；发送成功即把底层数组所有权转移给 worker。worker 处理完整个 batch 后清空长度并归还池，生产者不会在消费完成前复用。

如果 worker 跟不上：

1. batch channel 先达到 Q 个批次。
2. 剩余缓冲区被 worker 或生产者持有后，生产者无法继续取得空 buffer，或者阻塞在 channel send。
3. 生产停止向 `OrderStream` 取下一批数据，背压向上游传播。

合法订单不会因队列满而丢弃。核心在途订单内存量级为 `O((Q + W) × B)`，不随订单总数无限增长。`maxQueueDepthBatches` 记录观察到的最大 channel 积压，且不会超过 Q。

### 计划到达时间

生产者以 `pipeline.Run` 开始时间为基准，对每笔订单的 `PlannedArrivalNs` 使用可取消 timer 等待：

- `uniform-window` 和 `front-loaded-burst` 按步骤二生成的计划时间注入。
- `unbounded` 的计划时间全部为 0，不等待，用于快速正确性和纯吞吐测试。
- timer、取得 buffer 和 channel send 都监听 context。

批量发送会让 batch 内较早到达的订单等待同批最后一笔订单，这是降低 channel 调度开销所付出的批处理延迟；步骤七会比较不同 batch size 后再选参数。

### 正常关闭顺序

正常完成严格按照：

1. 生产者读到 OrderStream 结束。
2. 若最后一个 batch 未满，仍发送该 batch。
3. 生产者关闭订单 channel。
4. worker 继续读取直至 channel 排空并关闭，然后退出。
5. 主 goroutine 等待全部 worker。
6. 按 worker ID 合并私有统计，生成最终报告。
7. 验证五项守恒：

```text
generated == admitted == completed == requestedOrders
assignmentCount == requestedOrders
riderOrderCountSum == requestedOrders
```

任何一项不满足，运行不会被标记为成功。

### 取消、deadline 与 fatal panic

主程序使用 `signal.NotifyContext` 接收 Ctrl+C。`--timeout` 可以为整次运行增加 deadline，默认 `0s` 表示不主动设置 deadline。例如：

```powershell
go run ./cmd/matcher --arrival-model=uniform-window --timeout=45s
```

取消路径不承诺排空，但生产者等待时间、buffer 获取、channel send、worker receive 和每个 batch 内的订单循环都会检查 context。`pipeline.Run` 在所有 goroutine 退出后才返回部分结果，并在错误中报告：

```text
generated / admitted / completed / unfinished
```

worker 外层使用 `recover` 捕获 panic。错误包含 worker ID、当前订单 ID、Sequence 和 `debug.Stack()`；随后取消整条流水线。panic 对应订单不会被跳过后继续“成功”，整次运行必定失败。普通 Matcher 错误和生产者错误也遵循相同的全局取消规则。

### 确定性统计合并

worker 私有订单计数和 1 米距离直方图都是整数，合并顺序不影响结果。平均距离若直接合并多个 `float64` 局部和，最后几位会随订单分配到 worker 的方式变化。因此步骤六把最终距离四舍五入为微米，用 `uint64` 累加：

```text
distanceMicrometers = round(distanceMeters × 1,000,000)
averageMeters = totalMicrometers / 1,000,000 / assignmentCount
```

当前旧金山边界和一千万订单规模不会接近 `uint64` 上限；Observe 和 Merge 仍显式检查溢出。这样串行和并行报告的平均距离也能完全相等，而不是只能做浮点容差比较。

### 将 worker 私有计数落实为 `[]uint64`

### 结构内存估算

当前 amd64 构建中：

```text
sizeof(Order)   = 56 bytes
sizeof(Rider)   = 40 bytes
sizeof(KD node) = 96 bytes
buffer count    = channel capacity Q + workers W
```

程序输出的 `memoryEstimate` 使用：

```text

workerPrivateCountBytes  = W × N × 8
workerHistogramBytes     = W × 50,001 × 8

batchEnvelopeBytes       = (Q + W) × sizeof(admitted batch envelope)
orderBufferBytes         = (Q + W) × B × sizeof(Order)
```

其中订单总量 M 不参与公式。单元测试用完全相同的 N/W/Q/B 分别传入 1 单和 10,000,000 单，得到逐字段相同的估算。

### 完整指标采集的实现

每个订单使用同一个带 Go 单调时钟信息的 `runStarted` 作为基准，采集三个阶段：

```text
planned arrival -> admitted   admission delay
admitted -> completed         queue + match latency
planned arrival -> completed  end-to-end latency
```

生产者在 batch 真正写入有界 channel 后发布 admission 时间；worker 只有看到该时间后才开始处理，避免把等待空闲队列的时间漏算。生产者持有 admission 直方图，每个 worker 私有持有 queue/match 和 end-to-end 直方图，结束后由主 goroutine 合并，因此热路径没有共享直方图锁。

`admittedBatch` 信封和订单 slice 一起预分配在 `(Q+W)` 大小的固定池中循环复用；计划到达等待也由生产者复用一个 `time.Timer`。优化前 `batch-size=1` 会按订单创建信封和 timer；优化后 100,000 单测试的累计分配从约 14.61MiB 降至 1.64MiB，malloc 从约 166,772 次降至 2,210 次，避免为了低延迟引入千万级短命对象。

每个直方图使用 16 个 sub-bucket 的对数分桶，固定约 8KiB，不保存千万条时延。`min/max` 是精确观测值，P50/P95/P99 返回所在桶的保守上界。最终还输出：

- 计划到达窗口、实际完成注入时间和注入超窗量。
- 最后一单计划到达后到全部完成的排空时间。
- 实际 admission/completion rate。
- 三类直方图的样本数；正常完成时都必须等于订单总数。
- 最大 channel 积压批次数，以及生成/准入/完成/未完成守恒计数。

### batch 参数选择

首次用步骤六的吞吐参数 `batch-size=256` 运行基础档时，P99 端到端延迟约为 766ms。原因不是 KD-tree 查询慢，而是 333 单/秒时凑满 256 单理论上就需要约 0.768 秒。

因此将参数按测试目标拆开：

- 纯吞吐上限：`batch-size=256`，减少 channel 调度。
- 规定窗口实时延迟：`batch-size=1`，避免人为凑批；题目最大目标速率约 16,667 单/秒，远低于实测约 183 万单/秒的纯计算能力。

这是吞吐和实时延迟之间的显式参数权衡，不是为四档测试更换算法。四档仍使用相同 KD-tree、种子、2 workers 和 queue capacity 16。

## 当前原项目的启动方式和演示数据

这部分记录的是仓库原有网约车微服务，与独立 matcher 的启动方式不要混淆。

### 启动原项目

1. 准备 Docker Desktop、启用 Kubernetes，并安装 `kubectl` 与 Tilt。
2. 在 `infra/development/k8s/secrets.yaml` 中填写自己的 MongoDB URI；需要演示真实支付时，再填写自己的 Stripe 测试密钥。不要把真实密钥写入本文或提交到版本库。
3. 确认上下文并启动：

```powershell
kubectl config use-context docker-desktop
kubectl config current-context
tilt up
```

4. 用 `kubectl get pods -w` 等待主要 Pod 进入 `Running`。
5. 常用入口：Web `http://localhost:3000`、API Gateway `http://localhost:8081`、RabbitMQ 管理页 `http://localhost:15672`、Jaeger `http://localhost:16686`、Tilt 控制台通常为 `http://localhost:10350`。
6. 完整关闭开发环境使用 `tilt down`；只按 `Ctrl+C` 可能仍保留 Kubernetes 资源。

### 原项目演示流程与数据

1. 第一个浏览器标签页打开 Web，点击 `I Want to Drive`，选择一个车型（例如 `Sedan`），停留在 `Waiting for a rider...` 页面；司机标签页必须保持打开。
2. 第二个标签页点击 `I Need a Ride`。地图默认是旧金山，在地图上选择目的地并选择与司机相同的车型。
3. 乘客请求车辆后，回到司机标签页接收 `Trip request received!`，点击 `Accept trip`，再观察乘客端收到司机已分配状态。
4. 当前司机服务中的演示路线是旧金山附近的预定义经纬度，约为纬度 `37.77~37.79`、经度 `-122.41~-122.43`。步骤二据此把 matcher 测试边界固定为纬度 `37.70~37.82`、经度 `-122.52~-122.35`。
5. 使用占位 Stripe Key 时只能演示“司机上线 → 乘客报价/下单 → 司机接受”，不能演示真实 Checkout 和 Webhook。若接入自己的 Stripe 测试环境，官方常用测试卡为 `4242 4242 4242 4242`，有效期使用任意未来日期，CVC 使用任意三位数；不会产生真实扣款。

原项目当前按车型筛选后随机选司机；独立 matcher 的目的，是先在不改动微服务的情况下完成并证明“严格最近骑手”内核，再讨论接入。
