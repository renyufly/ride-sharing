## 步骤一：建立独立程序骨架

### 本步目标与边界

本步建立一个与现有微服务解耦的 `matcher` 命令。它不连接 RabbitMQ、MongoDB、Kubernetes 或 OSRM，只负责读取、校验并打印运行配置。

当前**没有**生成骑手和订单，也**没有**执行暴力匹配、KD-tree 查询或 goroutine 流水线。启动输出使用 `phase: "skeleton"` 和明确提示说明这一点，防止把程序“能启动”误认为算法已经完成。

### 目录与职责

```text
cmd/matcher/main.go                       独立命令入口
internal/config/config.go                 配置、默认值、命令行解析和校验
internal/config/config_test.go            配置单元测试
internal/model/model.go                   GeoPoint、Point2D、Rider、Order
internal/generator/doc.go                 步骤二占位包
internal/matcher/bruteforce/doc.go        步骤三占位包
internal/matcher/kdtree/doc.go             步骤五占位包
internal/pipeline/doc.go                  步骤六占位包
internal/report/doc.go                    后续报告能力占位包
```

占位包只有包说明，没有提前实现后续步骤。

### 具体实现过程

1. 新建 `cmd/matcher`，使算法练习可以用 `go run ./cmd/matcher` 单独启动，不受现有微服务基础设施影响。
2. 用独立的 `flag.FlagSet` 解析参数，而不是使用进程级全局 FlagSet。这样测试之间没有全局参数状态污染。
3. 配置包含骑手数、订单数、到达窗口、随机种子、算法、worker 数、batch 大小、channel 容量和匹配策略。
4. 第一版只允许 `nearest` 策略。`TopK` 与 `MaxExtraDistanceMeters` 字段已经在配置模型中保留，但必须为零，防止策略 A 完成前误启用策略 B。
5. 配置校验会一次收集并返回多个错误，例如骑手数为零且策略非法时，两项问题都能看到。
6. 将 `Order.ID` 与 `Order.Sequence` 分开建模：`ID` 用于业务幂等和追踪；`Sequence` 是单次运行中从零连续递增的顺序号，未来策略 B 可用它按序提交候选结果。
7. 对外位置使用 `GeoPoint{Latitude, Longitude}`；内部算法位置使用米制 `Point2D{X, Y}`。本步只冻结边界类型，坐标校验和投影属于步骤二。
8. 启动后以格式化 JSON 打印最终生效配置。到达窗口显示为 `30s`，避免 JSON 直接输出纳秒数造成误读。

### 配置默认值

| 配置 | 默认值 | 说明 |
| --- | ---: | --- |
| riders | 100 | 基础场景骑手数 |
| orders | 10,000 | 基础场景订单数 |
| arrival-window | 30s | 订单到达窗口 |
| seed | 42 | 后续确定性生成器的主种子 |
| algorithm | brute-force | 先为串行正确性基准预留 |
| workers | 1 | 当前仅记录，不启动 worker |
| batch-size | 128 | 当前仅记录，步骤六使用 |
| channel-capacity | 8 | 当前仅记录，步骤六使用 |
| strategy | nearest | 策略 A，当前唯一允许值 |
| topK / maxExtraDistanceMeters | 0 / 0 | 策略 B 尚未开放 |

配置中出现 worker、batch 和 channel 参数，不代表本步已经实现并发；它们只是提前固定可复现运行所需的完整配置面。

### 独立 matcher 的启动与演示

环境要求：本机 Go 版本满足根目录 `go.mod` 声明的 Go 1.25。

使用默认基础场景启动骨架：

```powershell
go run ./cmd/matcher
```

自定义一组只用于演示配置解析的数据：

```powershell
go run ./cmd/matcher --riders=12 --orders=34 --arrival-window=5s --seed=99 --algorithm=brute-force --workers=1 --batch-size=16 --channel-capacity=4 --strategy=nearest
```

预期输出的关键内容：

```json
{
  "phase": "skeleton",
  "message": "configuration accepted; matching is not implemented in step one",
  "config": {
    "riderCount": 12,
    "orderCount": 34,
    "arrivalWindow": "5s",
    "seed": 99,
    "algorithm": "brute-force",
    "workers": 1,
    "batchSize": 16,
    "channelCapacity": 4,
    "strategy": "nearest",
    "topK": 0,
    "maxExtraDistanceMeters": 0
  }
}
```

非法配置演示：

```powershell
go run ./cmd/matcher --riders=0 --strategy=balanced
```

matcher 进程会以退出码 `2` 结束，同时报告骑手数和策略两项校验错误；通过 `go run` 启动时，外层 Go 工具可能返回 `1` 并额外打印 `exit status 2`。该行为是 Admission Gate 的最小骨架，订单级输入校验将在步骤二实现。

### 本步测试数据与验证方式

本步没有真实骑手/订单测试数据；以下数据只验证配置边界：

| 用例 | 输入 | 预期 |
| --- | --- | --- |
| 默认配置 | 无参数 | 等于 `Default()` |
| 参数覆盖 | 12 骑手、34 订单、5 秒、种子 99、KD-tree、2 workers | 所有字段正确解析；这里只验证配置，不声称 KD-tree 已实现 |
| 多错误返回 | 0 骑手、`balanced` 策略 | 同时包含数量错误和策略错误 |
| 策略 B 保护 | `TopK=4` | 校验失败，直到策略 A 完成 |

运行本步测试：

```powershell
go test ./internal/config ./internal/model ./cmd/matcher
```

全仓库回归命令：

```powershell

```

## 当前原项目的启动方式和演示数据

这部分记录的是仓库原有网约车微服务，与独立 matcher 的启动方式不要混淆。

### 启动原项目

1. 准备 Docker Desktop、启用 Kubernetes，并安装 `kubectl` 与 Tilt。
2. 在 `infra/development/k8s/secrets.yaml` 中填写自己的 MongoDB URI；需要演示真实支付时，再填写自己的 Stripe 测试密钥。不要把真实密钥写入本文或提交到版本库。
3. 确认上下文并启动：

```powershell
kubectl config use-context docker-desktop
kubectl config current-context
tilt up
```

4. 用 `kubectl get pods -w` 等待主要 Pod 进入 `Running`。
5. 常用入口：Web `http://localhost:3000`、API Gateway `http://localhost:8081`、RabbitMQ 管理页 `http://localhost:15672`、Jaeger `http://localhost:16686`、Tilt 控制台通常为 `http://localhost:10350`。
6. 完整关闭开发环境使用 `tilt down`；只按 `Ctrl+C` 可能仍保留 Kubernetes 资源。

### 原项目演示流程与数据

1. 第一个浏览器标签页打开 Web，点击 `I Want to Drive`，选择一个车型（例如 `Sedan`），停留在 `Waiting for a rider...` 页面；司机标签页必须保持打开。
2. 第二个标签页点击 `I Need a Ride`。地图默认是旧金山，在地图上选择目的地并选择与司机相同的车型。
3. 乘客请求车辆后，回到司机标签页接收 `Trip request received!`，点击 `Accept trip`，再观察乘客端收到司机已分配状态。
4. 当前司机服务中的演示路线是旧金山附近的预定义经纬度，约为纬度 `37.77~37.79`、经度 `-122.41~-122.43`。这也是后续 matcher 确定城市边界时的项目依据之一，但步骤二尚未创建随机测试数据。
5. 使用占位 Stripe Key 时只能演示“司机上线 → 乘客报价/下单 → 司机接受”，不能演示真实 Checkout 和 Webhook。若接入自己的 Stripe 测试环境，官方常用测试卡为 `4242 4242 4242 4242`，有效期使用任意未来日期，CVC 使用任意三位数；不会产生真实扣款。

原项目当前按车型筛选后随机选司机；独立 matcher 的目的，是先在不改动微服务的情况下完成并证明“严格最近骑手”内核，再讨论接入。
