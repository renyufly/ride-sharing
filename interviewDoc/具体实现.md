## 步骤一：建立独立程序骨架

### 本步目标与边界

本步建立一个与现有微服务解耦的 `matcher` 命令。它不连接 RabbitMQ、MongoDB、Kubernetes 或 OSRM，只负责读取、校验并打印运行配置。

本步骤完成时还**没有**生成骑手和订单，也**没有**执行暴力匹配、KD-tree 查询或 goroutine 流水线。当时的启动输出使用 `phase: "skeleton"` 和明确提示说明这一点，防止把程序“能启动”误认为算法已经完成；当前命令已经随步骤二演进为数据生成预览，见下一节。

### 具体实现过程

1. 新建 `cmd/matcher`，使算法练习可以用 `go run ./cmd/matcher` 单独启动，不受现有微服务基础设施影响。
2. 用独立的 `flag.FlagSet` 解析参数，而不是使用进程级全局 FlagSet。这样测试之间没有全局参数状态污染。
3. 配置包含骑手数、订单数、到达窗口、随机种子、算法、worker 数、batch 大小、channel 容量和匹配策略。
4. 第一版只允许 `nearest` 策略。`TopK` 与 `MaxExtraDistanceMeters` 字段已经在配置模型中保留，但必须为零，防止策略 A 完成前误启用策略 B。
5. 配置校验会一次收集并返回多个错误，例如骑手数为零且策略非法时，两项问题都能看到。
6. 将 `Order.ID` 与 `Order.Sequence` 分开建模：`ID` 用于业务幂等和追踪；`Sequence` 是单次运行中从零连续递增的顺序号，未来策略 B 可用它按序提交候选结果。
7. 对外位置使用 `GeoPoint{Latitude, Longitude}`；内部算法位置使用米制 `Point2D{X, Y}`。本步只冻结边界类型，坐标校验和投影属于步骤二。
8. 启动后以格式化 JSON 打印最终生效配置。到达窗口显示为 `30s`，避免 JSON 直接输出纳秒数造成误读。

## 步骤二：实现确定性数据生成器

### 本步目标与边界

本步实现确定性骑手生成、流式订单生成、三种到达模型、三种空间分布、经纬度校验以及局部米制投影。`matcher` 现在会生成全部配置数量的骑手和订单，但只保留前三条数据用于 JSON 预览。

本步仍然**不选择骑手、不累计订单数、不执行 KD-tree，也不启动 goroutine 或按真实时间等待**。订单只记录 `PlannedArrivalNs`；步骤六的 CSP 生产者才负责等待计划时间、向有界 channel 投递并测量 admission delay。

```text

internal/generator/generator.go        确定性骑手生成器和流式 OrderStream

```

### 坐标模型与投影

测试城市边界框固定为：

```text
latitude:  37.70  ~ 37.82
longitude: -122.52 ~ -122.35
origin:     (37.76, -122.435)
earth R:    6,371,008.8 meters
```

该范围覆盖原项目的旧金山演示路线。所有骑手和订单共用边界框中心作为投影原点，并使用：

```text
x = R × (longitudeRadians - originLongitudeRadians) × cos(originLatitudeRadians)
y = R × (latitudeRadians  - originLatitudeRadians)
```

输入投影前必须满足纬度 `[-90, 90]`、经度 `[-180, 180]`，且两个值都不是 `NaN` 或正负无穷。边界框的四条边是包含关系。相同经纬度使用同一个投影器时会得到逐位相同的 `Point2D`。

### 可复现随机流

主种子默认是 `42`。生成器通过固定的 SplitMix64 finalizer 和不同的域常量派生 `riderSeed` 与 `orderSeed`。两个生成方法每次都从各自种子创建独立的 `rand.Rand`：

- 改变骑手数量或先后调用骑手生成，不会消费订单随机流。
- 相同主种子、边界框和参数重新创建 `OrderStream`，会从 `Sequence=0` 重放完全相同的业务 ID、位置和计划到达时间。
- 骑手 UID 从 `1` 连续递增；订单 `Sequence` 从 `0` 连续递增。
- 订单业务 ID 使用对 `orderSeed + Sequence` 的一一映射生成，和流水线排序字段分离且在单次数据集中不重复。

骑手一次性保存在切片中，因为空间索引需要完整骑手集合。订单由 `OrderStream.Next()` 每次构造一条；即使配置一千万订单，流对象本身也不保存一千万个订单。

### 到达模型

| 参数 | 行为 |
| --- | --- |
| `uniform-window` | 从 0 到完整窗口均匀安排，最后一单严格等于窗口末端 |
| `front-loaded-burst` | 约 80% 的订单安排在窗口前 20%，剩余订单分布在后 80% |
| `unbounded` | 所有 `PlannedArrivalNs` 都为 0，用于后续测纯吞吐 |

实现时曾由测试发现浮点换算导致 10 秒窗口的最后一单是 `9.999999999s`。现在对最后一个 Sequence 显式返回完整窗口，避免 1ns 的舍入误差。

### 空间数据分布

| 参数 | 用途 |
| --- | --- |
| `uniform` | 骑手或订单在整个边界框内均匀分布，作为标准验收数据 |
| `hotspot` | 85% 概率落在三个固定热点周围，其余保持均匀，用于订单热点测试 |
| `skewed` | 对归一化随机数做三次方变换，向边界框西南侧偏斜，用于骑手稀疏/倾斜测试 |

热点高斯采样可能越界，因此最终统一 clamp 到 `[0,1]` 后再映射进城市边界。测试会对三种分布逐点验证经纬度和投影结果。

## 步骤三：实现串行暴力匹配器

### 本步目标与边界

本步实现策略 A 的串行正确性基准：每来一笔订单，就扫描全部骑手，选择局部投影坐标中距离最近的骑手。该实现追求简单、确定和易于验证，后续 KD-tree 必须与它逐单对照。

本步只输出每笔订单的匹配结果以及生成数/匹配数，不累计每名骑手的订单数，不计算 Bottom 10、零订单人数、平均距离或 P95。这些属于步骤四。当前也没有 KD-tree、worker pool、channel 或真实到达时间等待。

### 新增和修改的代码

```text
internal/model/model.go                         新增通用 Assignment 结果模型
internal/matcher/bruteforce/matcher.go          串行暴力最近邻实现
internal/matcher/bruteforce/matcher_test.go     最近邻、平局、输入和规模测试
cmd/matcher/main.go                             逐单调用暴力匹配器并输出三条预览
```

### 具体实现过程

1. `bruteforce.New` 要求至少一名骑手，检查 UID 不重复，并拒绝含 `NaN` 或正负无穷的内部投影坐标。
2. 构造 Matcher 时复制骑手切片。测试期间骑手位置固定，复制后调用方不能在匹配过程中意外修改索引所依据的数据。
3. `Match` 只读取 `Order.Point` 与 `Rider.Point`，不读取原始经纬度，也不读取骑手历史订单数。
4. 距离比较使用：

```text
dx = order.Point.X - rider.Point.X
dy = order.Point.Y - rider.Point.Y
distanceSquared = dx × dx + dy × dy
```

只比较平方距离，不执行 `sqrt`。因为平方根在非负区间单调递增，距离平方最小的骑手就是实际距离最小的骑手，可以避免每个候选骑手一次不必要的开方。

5. 若 `candidateDistance < bestDistance`，替换当前最优骑手；若平方距离完全相等，仅当候选 UID 更小时替换。因此结果不依赖骑手切片顺序。
6. 返回的 `Assignment` 保留订单业务 ID、Sequence、骑手 UID 和平方距离。订单身份字段原样传递，方便后续检查遗漏、重复以及按序结果。
7. 主程序逐条读取 `OrderStream` 并立即匹配，不保存全部订单或分配结果；只保存前三条订单和 Assignment 用于演示。
8. 步骤三只支持实际执行 `brute-force`。配置层仍能识别未来的 `kd-tree` 枚举，但主程序会明确拒绝执行尚未实现的 KD-tree，避免静默回退或输出虚假结果。

### 正确性与复杂度

设骑手数为 `N`，订单数为 `M`：

- 单笔订单固定扫描 `N` 名骑手，时间复杂度为 `O(N)`。
- 全部订单时间复杂度为 `O(N × M)`。
- Matcher 持久保存静态骑手副本，构造期间临时使用 UID 集合检查重复，构建峰值空间复杂度为 `O(N)`；单次匹配额外空间为 `O(1)`。
- 主程序对订单保持流式处理，不因 `M` 增大而保存全部 Assignment。

这个版本不适合 `100,000 × 10,000,000`，因为需要约 `10^12` 次距离计算；它的价值是充当后续 KD-tree 的标准答案，而不是依靠更多 goroutine 掩盖算法复杂度。

### 本步测试数据与验证方式

| 用例 | 数据 | 验证点 |
| --- | --- | --- |

## 当前原项目的启动方式和演示数据

这部分记录的是仓库原有网约车微服务，与独立 matcher 的启动方式不要混淆。

### 启动原项目

1. 准备 Docker Desktop、启用 Kubernetes，并安装 `kubectl` 与 Tilt。
2. 在 `infra/development/k8s/secrets.yaml` 中填写自己的 MongoDB URI；需要演示真实支付时，再填写自己的 Stripe 测试密钥。不要把真实密钥写入本文或提交到版本库。
3. 确认上下文并启动：

```powershell
kubectl config use-context docker-desktop
kubectl config current-context
tilt up
```

4. 用 `kubectl get pods -w` 等待主要 Pod 进入 `Running`。
5. 常用入口：Web `http://localhost:3000`、API Gateway `http://localhost:8081`、RabbitMQ 管理页 `http://localhost:15672`、Jaeger `http://localhost:16686`、Tilt 控制台通常为 `http://localhost:10350`。
6. 完整关闭开发环境使用 `tilt down`；只按 `Ctrl+C` 可能仍保留 Kubernetes 资源。

### 原项目演示流程与数据

1. 第一个浏览器标签页打开 Web，点击 `I Want to Drive`，选择一个车型（例如 `Sedan`），停留在 `Waiting for a rider...` 页面；司机标签页必须保持打开。
2. 第二个标签页点击 `I Need a Ride`。地图默认是旧金山，在地图上选择目的地并选择与司机相同的车型。
3. 乘客请求车辆后，回到司机标签页接收 `Trip request received!`，点击 `Accept trip`，再观察乘客端收到司机已分配状态。
4. 当前司机服务中的演示路线是旧金山附近的预定义经纬度，约为纬度 `37.77~37.79`、经度 `-122.41~-122.43`。步骤二据此把 matcher 测试边界固定为纬度 `37.70~37.82`、经度 `-122.52~-122.35`。
5. 使用占位 Stripe Key 时只能演示“司机上线 → 乘客报价/下单 → 司机接受”，不能演示真实 Checkout 和 Webhook。若接入自己的 Stripe 测试环境，官方常用测试卡为 `4242 4242 4242 4242`，有效期使用任意未来日期，CVC 使用任意三位数；不会产生真实扣款。

原项目当前按车型筛选后随机选司机；独立 matcher 的目的，是先在不改动微服务的情况下完成并证明“严格最近骑手”内核，再讨论接入。
