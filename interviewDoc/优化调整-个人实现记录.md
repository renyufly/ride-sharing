# defer以及重试

给每一笔未完成订单一个明确去向：要么成功分配，要么进入 Deferred。

有两种 Deferred 原因。第一种是 `capacity_exhausted`，表示 Top-K 候选骑手都达到接单上限；第二种是 `window_expired`，表示订单轮到 Coordinator 最终决策时，已经超过本轮 Assignment Window。

Pipeline 只依赖一个 `DeferredOrderSink` 接口，不关心具体存储方式。CLI 模式使用 JSONL 文件，可以在程序退出后继续重放；Web 模式使用内存 Sink，便于页面直接发起下一轮 Retry。

etry 时不会重新随机生成订单，而是读取上一轮的 Deferred。订单 ID 和位置保持不变，Sequence 在新一轮重新编号，计划到达时间重置为 0。

|Web Session 只存在内存中，服务重启会丢失。



# Balanced策略

先为每个订单找到距离最近的 Top-K 骑手，再在距离可接受且未满额的候选中，优先选择当前接单量最少的骑手；候选搜索并行执行，最终分配按订单顺序串行提交。

原来的 Nearest 策略只选择最近骑手，匹配距离最优，但在订单分布不均匀时，热点区域的少数骑手会承担大量订单，其他骑手可能一直没有订单。

现Balanced：

- 第一步通过 KD-Tree 或 Brute Force 找到距离最近的 Top-K；
- 第二步以最近骑手的距离为基准，只保留不超过“最近距离加最大额外距离”的候选，然后优先选择当前接单量最少的骑手。  

最终选择规则是字典序的：先比较负载，负载相同再比较距离，距离也相同则选择 UID 更小的骑手。因此结果是确定性的。

并发方面，让多个 Candidate Worker **并行执行 Top-K 搜索**，但不允许 Worker 直接修改骑手负载。所有候选结果进入单个 Coordinator，Coordinator 按订单 Sequence 顺序提交，并独占骑手负载数组

核心实现位于 `internal/pipeline/balanced.go`

依次过滤和比较候选：

1. 超过最大允许距离：停止继续扫描。
2. 骑手达到容量上限：跳过。
3. 负载更低：替换当前选择。
4. 负载相同：距离更近者优先。
5. 距离仍相同：UID 更小者优先



# 系统设计

当前系统是一套“可重复压测、可观测、可延期重试”的单实例匹配实验平台。 支持不同订单到达模型、两种匹配策略、资源监控、骑手容量控制、Deferred 重试和前端可视化。

“Top-K 候选 + 负载决策 + Deferred”

```
前端实验页面
     │
     │ HTTP Run / Retry
     ▼
Matcher API
     │
     ▼
Match Runner
     │
     ├─ 生成骑手
     ├─ 创建空间索引
     ├─ 选择订单来源
     ├─ 启动资源监控
     └─ 启动 Pipeline
             │
             ├─ Producer
             ├─ 有界 Batch Channel
             ├─ Candidate Worker Pool
             └─ 单 Coordinator
                    │
                    ├─ Assignment
                    └─ Deferred Sink
```

Pipeline 是并发数据流：

```
OrderSource
    ↓
Producer （生成订单）
    ↓ 批量写入
Bounded Channel
    ↓
Candidate Workers （并行执行 Top-K 空间搜索）
    ↓
Coordinator
```

Producer 按计划到达时间生成订单，并通过有界 Channel 形成背压。

Candidate Worker 并行执行 Top-K 空间搜索。

Coordinator 按 Sequence 顺序处理乱序结果，独占骑手负载状态，执行最终分配。

## 可观测性

当前系统已经区分：

- Top-K 候选搜索时间。
- Coordinator 决策时间。
- 纯算法时间。
- Channel 排队加匹配时间。

## 当前设计的优点

可重复
固定 Seed、订单量、时间窗口和模型后，可以公平比较不同策略。
有界并发
Batch、Channel 和对象池都有容量，避免无界 Goroutine 和无界队列。
确定性
候选搜索可以乱序并行，但最终按订单 Sequence 顺序提交。
单写者负载模型
只有 Coordinator 修改骑手负载，不需要复杂锁竞争，也不会并发超额分配。
业务结果可审计
订单成功或 Deferred 都有明确去向，并且有守恒检查。
算法与存储解耦
Pipeline 只依赖 Source/Sink 接口，可以替换订单来源和 Deferred 存储。

## 缺点

1. 同步请求模型
一次 Run 要等整个实验完成才返回，不适合真实生产中的长任务和海量订单。
2. 单 Coordinator
它保证了确定性，但也形成单实例吞吐上限。
3. 状态只在内存中
骑手负载、Web Session 和当前轮次都没有共享持久化。
4. 无法安全水平扩容
如果启动多个 Matcher API 实例，Retry 请求可能落到没有 Session 的实例。
5. 容量是每轮累计值
没有真实订单生命周期，也没有“订单完成后释放骑手容量”。
6. 距离模型过于简化
当前主要使用空间投影直线距离，而生产系统更关心道路 ETA。
7. 没有完整幂等协议
还没有订单状态表、Assignment 唯一约束、预占令牌和消费确认，因此不能称为 Exactly-Once。
8. Deferred 机制仍偏实验性质
文件或进程内存不等同于生产级可靠队列。

# 分布式调度扩展

分布式调度不是把当前 Matcher Pod 从 1 个副本改成 3 个副本。真正需要解决的是：订单归谁处理、骑手状态归谁修改、多个节点如何避免重复分配，以及节点故障后任务如何接管。

单 Coordinator 会成为扩展瓶颈，而且骑手负载只存在当前进程内。

改成分布式：先按城市和地理区域对订单进行分片，订单事件进入消息队列后，同一分片只由一个 Scheduler 实例消费，这相当于把原来的单 Coordinator 扩展成多个区域 Coordinator。分片内部仍然保持单写者，分片之间可以并行处理。骑手必须有唯一 Owner Shard，其他区域即使把他查为候选，也必须向 Owner 申请带 TTL 和 fencing token 的 Reservation。只有预占成功，才能持久化 Assignment；失败就尝试下一个候选。

骑手实时位置和短期容量可以放在 Redis 或内存地理索引中。

节点宕机后，消息队列 Consumer Group 会把分区交给其他实例。











# 项目参考

> 由Claude生成，并非项目实际代码

单次匹配是微秒级，真正的瓶颈是内存，不是算力。
1000w 订单如果每单起一个 goroutine，栈 2KB 起步就是 20GB+，直接 OOM。题目说"约束的是堆栈空间"，考点就在这里。
因此设计原则是：goroutine 数量 O(核数)，不随订单数增长；订单流式处理，不落盘不留存，只保留每个骑手一个计数器。

总体架构（Pipeline + 分片 Actor）：

```
Producer ──batch──► Router ──┬─► Shard-0 (own riders + grid) ──┐
(按速率生成订单)  (按区域分片)  ├─► Shard-1 (own riders + grid) ──┼─► Merge → 后10名
                              └─► Shard-N ...                 ──┘
         有界channel(背压)         每个shard单goroutine独占状态，无锁
```

每个骑手状态（位置、订单数）只归属**一个** shard goroutine，所有修改都在这个 goroutine 内完成。shard 之间只通过 channel 传递订单批次。

调度器设计（重点）：

1.空间索引：均匀网格

把地图划成 G×G 网格，骑手按格子存下标 `[]int32`，找最近骑手 = **环形扩散搜索**：从订单所在格开始，逐圈向外查找

2.就近 + 负载均衡

3.分片与路由

分片数 S = GOMAXPROCS = 2，按网格行条带划分，每个 shard 独占一段区域。

Router 按订单坐标路由到对应 shard。

订单靠近分片边界时，最优骑手可能在隔壁 shard。home shard 算出局部最优后，如果 `bestCost > 到边界距离`，把"当前最优 + 代价上界"转发给邻居 shard。邻居更优就自己提交。

4.背压与优雅退出

Producer → Router → Shard 全部用**有界 channel**。下游慢，上游自然阻塞，内存有上界。

5.微批处理（降低 channel 开销）

channel 单次操作约 50–100ns，1000w 次逐单传递仍有可观开销。改为按 256 单一批传递，channel 操作降到约 4 万次。



## 内存预算（2C4G）

| 项                                            | D 场景估算              |
| --------------------------------------------- | ----------------------- |
| 骑手 10w × (Rider 12B + cnt 4B + 网格下标 4B) | ≈ 2MB                   |
| 网格                                          | 约 3.3 万格 × 24B ≈ 1MB |
| in-flight 订单：64×256×12B×2 层 channel       | ≈ 400KB                 |
| 订单结果                                      | **0**（只累加计数器）   |
| goroutine：producer + router + 2 shard        | 约 4 个，栈 ≈ 十几 KB   |

总计远低于 100MB，可以设置 `GOMEMLIMIT=3GiB` 作为兜底。



## 进阶

**为什么不"一单一协程"？**
 栈内存 ×1000w 会爆。协程适合并发的"角色"（流水线阶段、分片），不适合并发的"数据"。

**为什么不用全局 mutex 或 sync.Map？**
 热点竞争严重，2 核下锁开销大于计算本身。分片独占实现了无锁。

**为什么要微批处理？**
 把 1000w 次 channel 操作降到约 4 万次，并配合 `sync.Pool` 做到稳态零分配。

**纯就近 vs 均衡？**
 用 λ 做可调参数。可以展示不同 λ 下"后 10 名订单数"的变化，说明用数据驱动调参。

**瓶颈在哪？**

- 本题所有场景平均速率只有约 1.7w 单/s，单 goroutine 匹配即可吃下。
- 分片的价值在于水平扩展，以及突发峰值时用满 2 核。
- 真实**瓶颈是内存**，所以**关键是流式处理和背压**。

**如果继续扩展？**

- 骑手位置动态更新：独立的 `update` channel 汇入 shard，保持单写者原则。
- 骑手接单后占用容量，完成后释放。
- 订单超时重派，用 `time.Timer` 或时间轮，不要每单一个 Timer。
- 分片边界的精确转发协议（见 3.3）。
- 跨机器扩展时，按地理区域做一致性哈希。
- 批量最优匹配（匈牙利 / 最小费用流）：在每个小窗口内对局部订单-骑手子图求解，比逐单贪心更优，但代价更高。
