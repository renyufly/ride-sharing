# 骑手与订单匹配系统优化调整规划

## 一、目标与范围

本文针对 `internal/` 下的独立骑手匹配程序规划下一阶段优化，覆盖以下任务：

0. 生成器支持以 30 秒等时间窗口运行，并准确回答“X 秒内产生、准入、完成了多少订单”。
1. 单独监测匹配算法的实际计算耗时。
2. 在骑手存在订单容量上限时实现容量约束下的负载均衡。
3. 处理 30 秒窗口结束后仍未分配的订单。
4. 将单机调度演进为可扩展、可恢复的分布式调度。

本轮首先交付设计、指标口径、实施顺序和验收方案。后续实现应继续遵循 `interviewDoc/规范/`，尤其是有界内存、显式状态所有权、错误处理、可观测性、回滚和测试要求。

## 二、现状基线

当前实现已经具备以下能力：

- `internal/config` 默认配置是 100 名骑手、10,000 个订单、30 秒到达窗口。
- `internal/generator` 支持 `uniform-window`、`front-loaded-burst` 和 `unbounded` 三种到达模型，并通过固定随机种子生成可重放订单流。
- `internal/pipeline` 使用有界 Channel、批次池和 Worker Pool，具备背压、取消、部分结果和订单数量守恒检查。
- 策略 A 使用精确最近邻；策略 B 先并行计算 Top-K，再由单一 Coordinator 按订单 Sequence 顺序执行负载感知分配。
- 当前报告已经包含 `generated`、`admitted`、`completed`、`unfinished`，以及 admission、queue + match、end-to-end 三类延迟。
- 当前策略 B 的 `loads` 表示本次运行以来的累计分配数，仅用于相对均衡；它没有容量上限，也没有订单结束后的容量释放。
- 独立 matcher 当前与 RabbitMQ、MongoDB 和微服务解耦。仓库的微服务部分已经使用 RabbitMQ、MongoDB、OpenTelemetry 和 Kubernetes，可以作为分布式阶段的基础设施基线。

现有实现与本轮需求之间的主要差距如下：

| 需求 | 当前能力 | 主要缺口 |
| --- | --- | --- |
| X 秒生成统计 | 有计划到达窗口和累计计数 | `generated` 在等待计划到达前增加，不能直接解释为“窗口内已发出”；缺少窗口关闭时快照 |
| 实际匹配用时 | 有 `queueAndMatchLatency` | 排队、候选搜索、重排等待和最终决策混在一起，无法判断算法本身耗时 |
| 骑手容量 | 有累计负载均衡 | 没有硬容量、预占、释放、容量不足结果和异构容量公平性 |
| 剩余订单 | 取消时返回部分计数 | 内存中的剩余订单不可恢复；没有 pending、retry、expired 等业务状态 |
| 分布式调度 | 单进程单 Coordinator | 没有分片、幂等、跨节点容量一致性、故障恢复和再平衡 |

## 三、统一概念与统计口径

在实现具体任务前，应先冻结以下概念。否则“30 秒生成了多少”“30 秒没分完”会因为口径不同得到互相矛盾的结果。

### 3.1 30 秒包含两个不同概念

1. **到达窗口（arrival window）**：订单计划进入系统的时间范围。窗口结束代表停止产生新的计划订单，不代表所有订单必须在该时刻完成。
2. **处理期限（processing deadline）**：系统允许继续匹配和排空积压的最长时间。到期后仍未完成的订单进入待处理、过期或失败状态。

推荐默认语义：30 秒只表示到达窗口；窗口结束后允许继续排空。是否设置处理期限由单独参数控制，不能复用 `arrival-window`。

### 3.2 生成模式

保留现有固定订单数模式，并新增明确的按时长运行模式：

| 模式 | 必要输入 | 用途 | 结果是否可复现 |
| --- | --- | --- | --- |
| 固定数量 + 到达窗口 | 订单总数、窗口、到达模型 | 验证“10,000 单在 30 秒内到达” | 是 |
| 固定时长 + 目标速率 | 时长、每秒目标订单数、到达模型 | 验证不同稳定或突发流量 | 是 |
| 固定时长 + 尽力生成 | 时长、无速率上限 | 测试生成器或整条链路的最大吞吐 | 否，只能作为机器相关容量测试 |

固定时长模式建议采用半开区间 `[开始时间, 开始时间 + X)`：恰好落在 X 秒边界的订单不计入“X 秒内”。这样窗口快照不会因 Timer 唤醒先后产生边界歧义。现有固定数量模式可以保留兼容行为，但报告必须显示所用模式和边界语义。

仅给定“运行 30 秒”不足以得到可比较的订单量；还必须给定目标速率，或者明确这是“尽力生成”容量测试。

### 3.3 订单计数

报告中应区分：

- `planned`：窗口内计划产生的订单数。
- `generated`：OrderSource 已经物化的订单数。
- `emittedWithinWindow`：在窗口关闭前已由生成器发出的订单数。
- `admitted`：成功写入匹配流水线的订单数。
- `matchedWithinWindow`：窗口关闭前已经完成匹配的订单数。
- `eventuallyMatched`：包含排空阶段在内最终成功匹配的订单数。
- `deferred`：因无可用容量或处理期限到达而保留等待的订单数。
- `expired`：超过业务 TTL、不再允许分配的订单数。
- `failed`：因不可恢复的数据或系统错误进入失败终态的订单数。

窗口快照与最终结果必须同时存在。30 秒时的快照回答实时能力问题，排空后的最终结果回答订单是否丢失。

### 3.4 订单守恒

正常结束时应满足：

`planned = eventuallyMatched + deferred + expired + failed`

同时还要满足：

- 每个 Order ID 最多产生一个有效 Assignment。
- 每个容量预占必须对应一次提交或释放。
- 队列重投、进程重启和消费者重复投递不能造成重复占用骑手容量。

## 四、任务 0：按时长生成与窗口计数

### 4.1 目标

支持配置 30 秒或任意正时长，并在窗口关闭时准确输出这段时间内计划、生成、准入和完成的订单数量。固定种子、固定速率和固定到达模型下，计划订单序列必须可重放。

### 4.2 设计方案

1. 在配置层把“订单数量”“到达窗口”“生成模式”“目标速率”“处理期限”建模为独立概念，并进行互斥和组合校验。
2. 保留现有 `OrderStream` 的流式、常量内存特征，不预先构建全部订单。
3. 固定时长 + 目标速率模式根据时间片和速率计算下一笔订单的计划到达时间；不要通过每次浮点累加形成长期误差。
4. 生成器只负责确定订单内容和计划到达时间；Pipeline 继续负责真实等待、背压和准入。
5. 由 Pipeline 在窗口关闭的单调时钟时刻采集一次不可变快照，不能依赖 100ms 资源监控采样推算。
6. 保留当前累计字段以避免报告兼容性破坏，同时新增窗口快照字段。文档和字段说明必须禁止把 `generated` 直接当成吞吐。
7. 当背压严重时，`generated`、`emittedWithinWindow` 和 `admitted` 允许不同；这种差异本身就是容量信号，不能为了数字相等而提前生成并堆积到内存。

### 4.3 涉及模块

| 模块 | 规划职责 |
| --- | --- |
| `internal/config` | 新增生成模式、时长、速率和处理期限的配置表达与校验 |
| `internal/generator` | 提供按数量和按时长两种可重放计划，不负责睡眠和业务重试 |
| `internal/pipeline` | 记录真实发出、准入时间和窗口关闭快照 |
| `cmd/matcher` | 输出生成模式、边界语义、窗口快照和最终计数 |
| 对应测试 | 验证边界、取消、背压、零速率、极高速率和确定性 |

### 4.4 验收标准

- 默认场景仍能表达 10,000 单、30 秒窗口，不改变原有最近邻结果。
- 固定时长 + 固定速率的计划订单数符合定义，窗口边界不存在多一单或少一单。
- 人为降低匹配速度时，窗口快照能显示准入或完成落后，而不是错误报告“全部完成”。
- 固定 seed 重跑时，窗口内订单 ID、Sequence、位置和计划时间一致。
- 生成器内存占用不随计划订单总数线性增长。
- 报告能直接回答：“30 秒计划多少、实际发出多少、准入多少、匹配多少、排空后还剩多少”。

## 五、任务 1：监测算法实际匹配用时

### 5.1 指标拆分

当前 `queueAndMatchLatency` 应继续保留，用于观察用户实际等待，但需要新增纯算法阶段指标：

| 指标 | 起点 | 终点 | 是否包含排队 |
| --- | --- | --- | --- |
| `queueWait` | 订单准入 | Worker 开始处理 | 是，仅排队 |
| `candidateSearch` | 调用最近邻或 Top-K 查询前 | 查询返回后 | 否 |
| `assignmentDecision` | Coordinator 开始容量/负载选择 | Assignment 决定完成 | 否 |
| `algorithmCompute` | 每单搜索耗时与决策耗时之和 | 汇总值 | 否 |
| `reorderWait` | Top-K 结果产生 | 轮到该 Sequence 提交 | 是，策略 B 专属 |
| `endToEnd` | 计划到达 | 最终 Assignment | 是 |

策略 A 的 `algorithmCompute` 基本等于最近邻搜索耗时。策略 B 必须分别报告 Top-K 搜索与 Coordinator 决策；不能用两个分位数相加推导总分位数，应逐订单汇总计算量后再进入总算法直方图。

### 5.2 采集原则

- 使用 Go 单调时钟计算耗时，避免系统时间调整影响。
- 沿用固定内存直方图和 Worker 私有统计，结束后归并，避免在算法热路径争抢共享锁。
- 策略 B 的 Candidate Worker 记录搜索开始和结束，Coordinator 记录决策耗时并形成该订单的算法总耗时。
- 指标 Count 必须与实际完成订单数对应；取消运行时允许少于计划数，但必须等于已形成有效结果的样本数。
- 报告 P50、P95、P99、Max、样本数和累计计算时间。累计计算时间用于估算 CPU 工作量，不能与墙钟 Pipeline 时间直接等同。
- 对 10,000,000 单场景评估额外计时调用的观测开销。若全量采集明显影响吞吐，可增加明确的采样率，但基础 10,000 单验收应全量采集，报告必须显示采样率。

### 5.3 诊断价值

拆分后可以回答：

- 慢是 KD-tree/暴力查询本身慢，还是订单在 Channel 中等待。
- 策略 B 慢在 Top-K、Sequence 重排，还是单 Coordinator 决策。
- 增加 Worker 后算法计算是否不变，而 Queue Wait 是否下降。
- 骑手数量、Top-K 和空间分布变化对查询 P99 的影响。
- 进入分布式阶段后，网络和消息队列耗时是否掩盖了算法本身的收益。

### 5.4 验收标准

- 策略 A 和策略 B 均能单独输出纯算法 P50/P95/P99/Max。
- 注入人工 Matcher 延迟时，纯算法指标能反映该延迟；增加排队但不增加算法延迟时，只有 Queue Wait 上升。
- 策略 B 满足 `candidateSearch count = assignmentDecision count = algorithmCompute count = completed`。
- 新指标不改变匹配结果、订单守恒和现有延迟字段语义。
- 对比开启与关闭详细观测的基准，记录吞吐、分配次数和内存差异。

## 六、任务 2：有容量上限的负载均衡

### 6.1 首先明确“订单量限额”的业务语义

骑手限额至少有两种含义，不能混用：

1. **累计分配上限**：一次测试中骑手最多接收 N 单，适用于纯算法演示。一旦达到上限，本轮不再释放。
2. **并发进行中订单上限**：骑手同时最多承担 N 单，订单完成、取消或预占超时后释放容量，适用于真实调度。

生产设计应采用第二种。为了使独立 matcher 可重复验证，可增加确定性的订单服务时长模型来模拟容量释放；如果暂时不模拟完成事件，则必须明确当前测试的是累计上限，并保证总容量足够或预期产生 deferred 订单。

### 6.2 状态模型

静态地理信息与动态调度状态应分离：

- 静态 Rider：UID、位置、车型/能力标签。
- 动态 RiderState：容量上限、已预占数、进行中订单数、可用状态、状态版本、最后更新时间。
- AssignmentReservation：Order ID、Rider UID、预占版本、租约到期时间、状态。

容量不能直接加入只读 KD-tree 节点并由多个 Worker 修改。Candidate Worker 仍只做空间候选查询；Coordinator 是单机模式下动态状态的唯一写入者。

### 6.3 选择规则

推荐按以下顺序筛选和比较：

1. 过滤离线、车型不兼容、位置过期或容量已满的骑手。
2. 在最大额外距离范围内寻找可用候选。
3. 不同骑手容量不一致时，以 `当前占用 / 容量上限` 的负载率比较，而不是只比较订单绝对数。
4. 负载率相同时比较当前占用数，再比较距离，最后用 Rider UID 稳定打破平局。
5. 选中后先预占容量，再发布 Assignment；发布失败或租约超时必须释放预占。

Top-K 内全部满载时，不应立即把订单判为永久失败。建议采用分层降级：

- 第一层：在原 Top-K 与额外距离限制内选择。
- 第二层：按配置扩大候选数量或相邻地理网格，但仍遵守最大业务半径。
- 第三层：没有可用容量时将订单转为 `WAITING_CAPACITY`，等待容量释放事件后重试。
- 订单超过 TTL 后才进入 `EXPIRED`；数据非法或超过重试预算的技术错误才进入失败/DLQ。

### 6.4 容量生命周期

建议状态流转：

`AVAILABLE → RESERVED → ACTIVE → RELEASED`

异常分支包括：

- 预占后 Assignment 发布失败：回滚或由租约到期释放。
- 骑手拒单：释放容量，订单重新进入待匹配。
- 订单取消：幂等释放容量。
- 行程完成：幂等释放容量。
- 骑手掉线：停止新预占；已有 Reservation 按业务规则转移或等待租约。

释放操作必须携带 Order ID/Reservation ID，并具有幂等性，避免重复完成事件造成容量减成负数。

### 6.5 报告扩展

新增容量相关指标：

- 可用总容量、已使用容量和容量利用率。
- 满载骑手数、零负载骑手数。
- 每名骑手的负载率分布和负载率 CV。
- 因容量过滤的候选数。
- Top-K 内无容量次数、扩大搜索次数、等待容量订单数。
- Reservation 创建、提交、释放、过期和冲突次数。
- 匹配距离相对无容量约束基线的变化。

### 6.6 验收标准

- 任意时刻每名骑手的 `reserved + active` 不超过容量上限。
- 总容量不足时，多余订单进入明确的等待或过期状态，不丢失、不重复分配。
- 容量释放后，等待队列中的订单能够重新调度。
- 骑手容量不同的场景按负载率均衡，不会因为高容量骑手绝对订单数较大而被错误惩罚。
- 固定输入和固定完成事件序列下，结果可重放。
- `maxExtraDistance`、车型/能力过滤和最近邻正确性继续受保护。

## 七、任务 3：30 秒后仍未分配订单的处理

### 7.1 推荐策略：停止生成，但继续有界排空

30 秒到达窗口结束时执行以下步骤：

1. 停止产生新订单并记录窗口快照。
2. 已准入 Pipeline 的订单继续匹配。
3. 因瞬时拥塞产生的积压在可配置的 Drain Grace Period 内排空。
4. 因骑手容量不足而无法分配的订单进入 `WAITING_CAPACITY`，不占用计算 Worker 空转重试。
5. Drain Grace Period 到期后仍未完成的订单写入持久化待处理队列，并在最终报告中计入 `deferred`。

窗口结束不应直接取消整个 Context。当前 `RunTimeout` 会终止 Producer 和 Worker，适合故障保护，但不应等同于正常的窗口关闭。

### 7.2 待处理订单状态机

建议业务状态至少包含：

- `PENDING`：已接收，尚未开始匹配。
- `MATCHING`：正在计算候选或尝试预占。
- `WAITING_CAPACITY`：当前候选范围内没有容量，等待事件触发。
- `RESERVED`：已预占骑手容量，等待 Assignment 提交确认。
- `ASSIGNED`：分配成功终态。
- `EXPIRED`：超过订单 TTL。
- `FAILED`：不可恢复错误或超过技术重试预算。
- `CANCELLED`：用户取消终态。

状态变更必须使用 Order ID 做幂等条件更新。重试时从持久化状态恢复，不能只依赖进程内 Channel。

### 7.3 重试触发

优先使用事件驱动，定时扫描作为兜底：

- 骑手完成订单、取消 Reservation 或重新上线时，触发对应地理分片的容量可用事件。
- 等待队列按订单创建时间、业务优先级和重试次数组织，避免新订单持续插队导致旧订单饥饿。
- 技术故障采用带抖动的指数退避，并设置最大重试次数。
- “暂无骑手容量”是业务可恢复状态，不应进入 DLQ；消息损坏、协议不兼容等不可处理错误才进入 DLQ。

### 7.4 背压与过载保护

- 有界内存队列满时，入口应降速或拒绝新的低优先级请求，不能创建无限 goroutine 或无限 Channel。
- 记录 backlog depth、oldest order age、retry rate 和 capacity wait time。
- 当积压超过阈值时，可扩大搜索半径、调整优先级、触发运力告警或返回明确的“暂无运力”。这些必须是显式业务策略，不能静默改变最近邻规则。
- 对订单设置 TTL，避免已经失去业务价值的订单无限重试。

### 7.5 单机演示与生产处理的区别

| 场景 | 剩余订单保存方式 |
| --- | --- |
| 独立 matcher 基准程序 | 输出数量、Sequence 范围和状态汇总；保持有界内存，不保存全部 Assignment |
| 生产调度 | 将每个 Order ID、状态、重试时间、版本和 Reservation 持久化，并通过消息队列恢复 |

独立 matcher 的 `unfinished = expected - completed` 只能作为数量统计，不能证明订单可恢复。分布式阶段必须通过持久化状态和重启测试证明恢复能力。

### 7.6 验收标准

- 30 秒窗口结束时能立即得到快照，同时 Pipeline 可继续排空。
- 人为降低处理能力后，最终满足订单状态守恒，未分配订单都有可查询状态和原因。
- 容量恢复事件可以唤醒待处理订单，且不会产生重复 Assignment。
- 进程在订单处于 PENDING、MATCHING、RESERVED 三个阶段分别崩溃后，重启均能恢复或安全重试。
- 过期订单不再分配，技术失败和容量不足进入不同指标与处理通道。

## 八、任务 4：分布式调度

### 8.1 演进原则

- 保留 `internal/matcher` 的纯候选搜索能力，不让算法包直接依赖 RabbitMQ、MongoDB 或网络协议。
- 将“候选搜索”“容量状态”“订单状态机”“消息适配器”拆成不同职责。
- 初期采用每个分片单写者，延续当前 Coordinator 的状态所有权模型，避免直接把单机 `loads` 改成跨节点共享数组或分布式锁。
- 消息系统按至少一次投递设计，业务层通过幂等状态转换实现“有效一次”Assignment。

### 8.2 推荐架构

```text
订单入口
  │
  ▼
持久化订单 + Outbox
  │
  ▼
RabbitMQ 路由交换机
  │（城市 / Geohash 分片）
  ├────────► Shard Queue 1 ─► Scheduler Leader 1 ─► 本地空间索引
  ├────────► Shard Queue 2 ─► Scheduler Leader 2 ─► 本地空间索引
  └────────► Shard Queue N ─► Scheduler Leader N ─► 本地空间索引
                                  │
                                  ▼
                         容量预占 + Assignment Outbox
                                  │
                                  ▼
                        Trip / Driver Service 事件流
                                  │
                                  └── 完成、拒绝、取消、上线事件回流
```

仓库已有 RabbitMQ、MongoDB、OpenTelemetry 和 Kubernetes。本项目第一阶段优先复用这些设施，避免同时引入多套消息系统。若后续证明 MongoDB 条件更新或单写者吞吐不足，再评估 Redis 原子预占或日志型消息系统，不能在没有指标前增加基础设施复杂度。

### 8.3 分片策略

推荐先按城市，再按固定精度 Geohash 或规则网格分片：

- Order 根据上车点进入主分片。
- Rider 根据当前位置归属一个 Home Shard；位置跨界时发布版本化迁移事件。
- 主分片先搜索本地骑手；靠近边界或本地无容量时查询相邻分片。
- 分片键和边界规则必须版本化，所有节点使用相同配置。
- 热点分片通过拆分网格扩容；低流量分片可以合并，但重分片期间必须避免 Rider 同时被两个分片视为可预占。

不建议直接按 Order ID 哈希，因为这会破坏空间局部性，使每次匹配都需要跨节点查询大量骑手。

### 8.4 单写者与扩容

第一阶段每个地理分片只允许一个逻辑 Coordinator 持有可变 RiderState：

- Kubernetes 可以运行多个实例，但同一分片只有一个持有租约的 Leader 消费并提交分配。
- Leader 故障时，备实例取得租约，从持久化 RiderState、Reservation 和事件位点恢复。
- 横向扩容优先增加分片数，而不是让多个实例并发修改同一分片容量。

如果单分片吞吐达到瓶颈，再演进为主动-主动预占：使用带版本号的条件更新或原子脚本执行“检查容量并增加 Reservation”。普通的先读后写、单独原子计数或跨节点互斥锁均不足以保证复合选择的一致性。

### 8.5 消息可靠性与幂等

- Order ID 是业务幂等键，Sequence 只用于一次基准运行内的顺序和诊断。
- 消费者只有在订单状态与 Assignment Outbox 持久化成功后才确认消息。
- Assignment 发布采用 Outbox，避免数据库提交成功但消息发布失败造成“已占容量但下游不知道”。
- 重复消费同一订单时读取现有终态；已有有效 Assignment 时直接返回同一结果，不再次占用容量。
- Reservation 使用唯一 ID、Order ID、Rider UID、版本和租约时间。提交、释放和过期均为幂等转换。
- DLQ 只存不可处理或超过技术重试预算的消息，并记录原始错误、重试次数和协议版本。

### 8.6 跨分片匹配

跨分片采用逐级扩大而非全局广播：

1. 主分片查询本地 Top-K。
2. 距离边界较近或本地无容量时查询必要的相邻分片。
3. 合并候选后仍按距离、容量和稳定 UID 规则选择。
4. 对远端 Rider 的容量预占由 Rider Home Shard 或统一原子状态存储确认。
5. 预占冲突时重新选择下一个候选，限制最大尝试次数，之后进入等待状态。

必须记录跨分片查询率、预占冲突率和额外网络延迟。若跨分片比例长期过高，说明分片精度、热点边界或 Rider 归属策略需要调整。

### 8.7 可观测性

每个订单应使用同一 Trace ID 贯穿入口、RabbitMQ、Scheduler、容量预占和 Assignment 发布。至少暴露：

- 每个分片的输入速率、完成速率、队列深度、最老消息年龄。
- 纯算法耗时、消息等待、状态存储耗时、预占耗时和端到端耗时。
- 本地/跨分片匹配比例、候选数量、搜索半径。
- 容量利用率、满载骑手数、等待容量订单数。
- 幂等命中、重复消息、预占冲突、租约过期、重试和 DLQ 数量。
- Leader 切换次数、恢复时长、消费位点落后量。

告警应重点关注 backlog age、未匹配率、P99、容量冲突、DLQ 增长和分片热点，而不仅是 CPU、内存。

### 8.8 分布式验收场景

- 两个以上调度实例、多个地理分片下，固定订单集没有重复 Assignment。
- 同一订单重复投递至少两次，最终只占用一个骑手容量。
- Scheduler 在预占前、预占后、Outbox 发布前和消息确认前分别崩溃，恢复后状态仍一致。
- Leader 切换期间允许短暂延迟，但不能超卖容量或丢订单。
- Rider 跨分片移动时不能同时被两个分片成功预占到超过容量。
- 热点分片产生背压时，其他分片继续服务，不发生全局阻塞。
- 30 秒 10,000 单场景输出窗口快照和最终结果；再逐步扩大到现有四档规模。

## 九、面试展示前端

在现有 `web` 项目新增 `/matcher` 路由，不另建前端，也不接入原网约车的行程、支付和 WebSocket 状态。页面复用 React Leaflet 地图，仅作为独立 matcher 的可视化外壳。

后端将 `cmd/matcher` 的运行编排提取为 CLI 与 HTTP 共用的 Runner，并提供同步的 `POST /matcher/run`。第一版同一时间只运行一个任务，忙碌时返回明确错误，避免多次实验竞争 CPU、内存和 GC，影响 2 核场景的指标可信度。正式的 2 核/4GB 结论仍以容器资源限制报告为准。

页面参数包括骑手数、订单数、到达窗口与模型、随机种子、空间分布、算法、策略、Worker、Batch、Channel 容量，以及策略 B 的 Top-K、最大额外距离和骑手订单上限；高级参数默认折叠。服务端文件路径等内部参数不向浏览器开放。

展示内容包括：

- 地图上的骑手、订单抽样点和匹配连线，明确标注抽样数量并设置硬上限。
- 订单生成、准入、完成、未完成和 deferred 计数及守恒检查。
- 吞吐、注入速率、排空时间，以及 admission、queue + match、end-to-end 和纯算法延迟。
- Bottom 10、零订单骑手数、最小/平均/最大订单数、方差、CV 和匹配距离。
- 索引大小、内存估算、Heap、GC、goroutine 等资源指标。
- 策略 B 的候选队列、重排窗口、容量过滤和 deferred 原因。
- 可折叠的原始 JSON，便于现场核对指标来源。

面试默认使用 100 名骑手、10,000 笔订单的 `unbounded` 快速场景，先展示严格最近策略 A，再用相同 seed 展示策略 B 的公平性与距离成本。真实 30 秒窗口和最大规模结果使用已验证报告，不在现场重复长时间压测。

## 十、建议实施顺序

### 阶段 0：冻结口径和基线

- 冻结生成模式、窗口边界、状态机、容量语义和订单守恒公式。
- 保存当前策略 A/B 的正确性、吞吐、延迟、内存和公平性报告作为回归基线。
- 明确 30 秒是到达窗口还是硬处理期限；本文默认是到达窗口。

### 阶段 1：窗口生成与精确计数

- 完成任务 0。
- 先解决窗口快照和最终结果的区分，再进入容量和分布式工作。
- 保持现有固定数量模式向后兼容。

### 阶段 2：算法耗时拆分

- 完成任务 1。
- 用指标确定搜索、Coordinator 和排队各自占比，作为后续分片和扩容依据。

### 阶段 3：单机容量约束

- 完成任务 2 的单 Coordinator 版本。
- 先验证硬容量、预占、释放、等待和幂等，再把状态搬到分布式环境。

### 阶段 4：剩余订单和恢复

- 完成任务 3。
- 在独立 matcher 中验证状态守恒；在集成环境中增加持久化、重试、TTL 和崩溃恢复。

### 阶段 5：分布式分片调度

- 完成任务 4 的 RabbitMQ + MongoDB 最小版本。
- 首先使用每分片单写者，然后根据纯算法耗时、队列积压和状态存储耗时决定是否需要主动-主动容量预占。

### 阶段 6：压测、灰度与回滚

- 对固定数量、固定速率、突发、容量不足、热点分片和故障注入分别压测。
- 灰度时保留旧随机/最近邻调度路径作为 Feature Flag 回退方案。
- 上线前准备队列、状态表、索引、配置版本、监控面板和回滚步骤。

## 十一、总体完成定义

只有同时满足以下条件，才能认为本轮优化完成：

1. 能准确回答任意 X 秒窗口内计划、生成、准入、匹配和剩余的订单数。
2. 能把纯算法耗时与排队、重排、消息和状态存储耗时分开。
3. 骑手容量永不超卖，预占和释放可审计、可幂等、可恢复。
4. 30 秒后未完成订单不会被静默丢弃，均有明确状态、原因和后续策略。
5. 分布式重复投递、节点崩溃、Leader 切换和分片迁移不会造成重复 Assignment 或容量泄漏。
6. 策略 A 的精确最近邻正确性与策略 B 的距离保护不回退。
7. 内存仍然有界，队列、重试和 goroutine 均有明确上限与背压策略。
8. 单元测试、竞态检测、静态检查、故障注入和受限资源压测均通过，并保留可复现报告。
