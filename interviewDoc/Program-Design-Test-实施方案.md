# Program Design Test：骑手与订单匹配系统实施方案

## 1. 题目与目标

使用 Go 的 goroutine、channel 和 CSP 并发模型，实现骑手与订单的匹配系统设计。

基础场景：

- 随机构建 100 名不同骑手（uid,位置），每名骑手包含 UID 和位置。
- 30 秒内产生 10,000 笔突发订单。
- 系统先按就近原则为每笔订单分配骑手，并在资源约束下尽可能缩短完成时间。
- 统计并输出累计分配订单最少的 10 名骑手及其订单数。

扩展测试：

| 场景 | 骑手数 | 订单数 | 到达窗口 | 平均到达速率 |
| --- | ---: | ---: | ---: | ---: |
| 基础 | 100 | 10,000 | 30 秒 | 约 333 单/秒 |
| 扩展一 | 1,000 | 100,000 | 1 分钟 | 约 1,667 单/秒 |
| 扩展二 | 10,000 | 1,000,000 | 3 分钟 | 约 5,556 单/秒 |
| 扩展三 | 100,000 | 10,000,000 | 10 分钟 | 约 16,667 单/秒 |

理论资源限制：2 核 CPU、4GB 内存。要求：在最短和最少的约束条件下，机器资源理论上是2核心4G内存。

本方案先实现独立、可验证的单机匹配程序。核心算法和性能得到验证后，再考虑接入现有网约车微服务。参考资料为：interviewDoc\Golang 任务调度与优先级队列实战：从能跑到生产可用.md ，只用于借鉴有界并发、背压、监控和优雅停机思路，不将其中代码或结论直接视为本题要求。

## 2. 首先确认题意

正式编码前，确认以下问题：

1. 时间窗口表示订单在这段时间内到达，还是所有订单必须在此时间内完成匹配：本方案将其解释为订单到达窗口。所有订单在窗口内产生，订单从计划到达、实际入队到完成分配的时间分别统计。
2. 一名骑手是否可以累计分配任意数量的订单：可以累计分配多个订单。“输出订单最少的 10 名骑手”只是统计要求，不等于系统必须均匀分单。题目没有规定骑手最低订单量，因此零订单是合法结果，Bottom 10 必须包含零订单骑手。
3. 骑手和订单位置使用二维平面坐标还是经纬度：当前微服务项目使用的是 **经纬度**。对外模型继续使用 `latitude/longitude`；匹配器在边界处把经纬度转换为以米为单位的内部平面坐标，再执行暴力基准和 KD-tree 查询。
4. 一次测试期间骑手位置是否保持不变：假设 **固定不变**
5. “就近原则”是否要求严格找到全局最近骑手：策略 A 必须返回投影距离的精确全局最近骑手，KD-tree 只是减少搜索范围，不能改变结果。近似最近邻不进入第一版。
6. 多名骑手与订单距离相同时如何选择：策略 A 的 Baseline 严格按 UID 选择，保证串行与并发结果确定且便于验证；策略 B 才引入实时负载，负载相同后再按距离和 UID。
7. 2 核 4GB 是否包含订单生成器、结果记录和监控开销：最保守的工程假设是 **整个被测程序总资源限制为 2 Core / 4GB**，包括生成、匹配、统计等；不要假设 matcher 可以独占 4GB。
8. 是否需要保存每笔订单的匹配结果，还是只要求最终统计：题目明确要求的是最终 **后10名骑手及其订单数**，没有要求保存 1000 万笔 assignment。因此建议 streaming 处理，只累计 Rider 的订单数和性能统计，不保存全部结果。
9. 大规模测试中的时间是订单到达时间，还是程序完成全部匹配的截止时间：题目没有给出独立的完成截止时间，因此将到达窗口、最后一单到达后的排空时间和总完成时间分开报告。

- 使用经纬度作为输入模型，在算法内部统一投影为局部二维平面坐标，并使用投影后的欧氏距离定义“就近”。

Bottom 10 是骑手分配公平性的观测指标，但不能单独证明算法不公平。大量骑手获得 0/1 笔订单，可能来自订单热点、骑手空间分布或纯就近规则本身。第一版优先实现策略 A，得到可信的纯就近基线；只有完成策略 A 的正确性和性能验收后，才实现策略 B，引入实时负载因素，并通过 Bottom 10、零订单骑手数、订单数方差、变异系数和平均/P95 匹配距离量化公平性与距离成本的 trade-off。

以上内容作为第一版已经冻结的实现假设，不再阻塞编码。如果面试官后续明确要求骑手容量、动态位置、道路 ETA、订单优先级或固定完成 deadline，需要重新评估状态模型和验收标准，不能在现有假设下悄悄改变语义。

### 2.1 位置模型现状与本题决策

#### 当前项目使用经纬度

现有项目不是使用任意的笛卡尔 `x/y` 坐标，而是使用真实地理经纬度：

- `proto/driver.proto` 中的 `Driver.Location` 明确定义为 `latitude` 和 `longitude`，并同时保存 Geohash。
- `services/driver-service/utils.go` 中的预定义路线是旧金山经纬度，例如纬度约 `37.78`、经度约 `-122.42`。
- `proto/trip.proto` 中的 `PreviewTripRequest.startLocation` 和 `endLocation` 使用同样的经纬度结构。
- API Gateway 和前端把用户的 pickup、destination 作为 `latitude/longitude` 传入 Trip Service。

经纬度虽然由两个数值组成，但不是等比例的二维平面坐标。纬度一度和经度一度对应的地面距离不同，经度尺度还会随纬度变化。因此不能直接使用下面的公式并宣称它代表严格的地理距离：

```text
(latitude₁ - latitude₂)² + (longitude₁ - longitude₂)²
```

#### 本题采用“对外经纬度、内部投影坐标”

原项目的 protobuf、HTTP 和事件边界继续使用：

```go
type GeoPoint struct {
    Latitude  float64
    Longitude float64
}
```

匹配器入口先完成范围校验：

```text
-90  <= latitude  <= 90
-180 <= longitude <= 180
```

然后以测试城市中心 `(lat0, lon0)` 为固定原点，把经纬度转换为局部平面米制坐标：

```text
x = R × (longitudeRadians - lon0Radians) × cos(lat0Radians)
y = R × (latitudeRadians  - lat0Radians)
```

其中 `R` 为地球平均半径。骑手和订单必须使用同一个固定原点和同一套转换参数，不能为每个点单独选择原点。

第一版固定使用 `EarthRadiusMeters = 6,371,008.8`，投影原点取配置城市边界框中心。地球半径、边界框和原点都写入运行报告，避免测试配置不透明。

匹配器内部只使用：

```go
type Point2D struct {
    X float64 // meters
    Y float64 // meters
}
```

本题的“严格最近”定义为：在同一局部投影坐标系中，欧氏距离最小的骑手。该定义适用于本项目的城市局部场景，也允许暴力基准与 KD-tree 使用完全相同的距离函数进行逐单对照。

如果测试范围扩大到跨城市、极区或跨越 `±180°` 经线，则局部投影不再适用。此时应将经纬度转换为三维单位球坐标，在三维 KD-tree 中比较平方弦长，或使用能为球面距离提供正确下界的空间索引。本次一周实现不同时维护两套空间模型。

#### “就近”的业务边界

本题默认“就近”是地理直线距离，不是道路行驶时间。道路最近需要调用 OSRM 等路网服务计算候选骑手到上车点的 ETA，无法仅凭一个二维 KD-tree 直接得到。

如果后续要求按道路 ETA 派单，推荐采用两阶段策略：

1. 使用空间索引快速召回距离最近的 `K` 名候选骑手。
2. 使用 OSRM Table 或路网服务计算候选骑手到上车点的实际时间，再选择 ETA 最小者。

这样可避免对 10 万名骑手逐一请求路线服务。

#### 原项目定义是否需要修改

独立完成本题时，不需要修改现有 protobuf 或微服务模型。matcher 定义轻量的 `GeoPoint` 输入和内部 `Point2D`，通过适配器完成转换即可。

正式接入现有微服务时，不应把所有 `latitude/longitude` 改名为 `x/y`，而应进行以下最小改造：

1. 保留 `Driver.Location`、Trip 坐标和 Geohash 作为对外地理模型。
2. 在 `Trip` 或专用 `MatchOrder` 事件中增加明确的 `pickupLocation`，不要依赖 `route.geometry[0].coordinates[0]` 推断上车点。
3. 在 Driver Service 内部建立经纬度到 `Point2D` 的适配层和只读索引快照。
4. 为骑手位置补充 `UpdatedAt` 和可用状态；正式派单时排除位置过期、不可用或车型不匹配的骑手。
5. protobuf 只追加新的字段编号，并通过 protobuf 工具重新生成 `*.pb.go`，不手工修改生成文件。

#### 当前坐标链路中需要先修正的问题

[OSRM HTTP API](https://project-osrm.org/docs/v26.4.0/http) 的请求坐标和 GeoJSON 坐标顺序是 `[longitude, latitude]`。项目构造 OSRM URL 时使用 `longitude, latitude`，但 `services/trip-service/pkg/types/types.go` 的 `OsrmApiResponse.ToProto()` 当前把 `coord[0]` 写入 `Latitude`、把 `coord[1]` 写入 `Longitude`，顺序相反。

接入匹配算法前应统一边界转换：

```go
Latitude:  coord[1]
Longitude: coord[0]
```

本地 mock 路线也必须使用和 OSRM 原始响应相同的 `[longitude, latitude]` 顺序，否则真实 OSRM 与 mock 模式会产生不同语义。

此外，前端已经通过 WebSocket 发送骑手位置，但 `services/api-gateway/ws.go` 当前对 `DriverCmdLocation` 只保留了“未来处理”的注释，Driver Service 中的骑手位置实际上只在注册时随机初始化。静态压测可以沿用“测试期间位置固定”的假设；如果要声称支持真实移动骑手，则必须实现位置更新、过期判断以及空间索引的更新或快照重建。



## 3. 验收标准

### 3.1 策略 A：纯就近 Baseline 正确性

- 每笔订单恰好分配一次。
- 选择结果是投影坐标系中的全局最近骑手。
- 距离相同时严格按 UID 规则处理。
- 所有骑手的累计订单数之和等于已完成匹配的订单总数。
- 零订单是合法结果，不设置骑手最低订单量。
- 最少 10 名的统计包含零订单骑手。
- 相同随机种子和配置产生相同结果。
- 串行版本与并发版本产生完全相同的骑手计数。
- 暴力扫描与 KD-tree 对同一输入逐单产生相同骑手 UID。

策略 A 是第一版必须完成的核心交付。策略 B 不得阻塞、替代或弱化策略 A 的正确性与性能验收。

### 3.2 策略 B：负载感知扩展正确性

- 只在策略 A 完成后实现和验证。
- 每笔订单仍然恰好分配一次。
- 候选集合由 KD-tree 的 Top-K 最近邻产生。
- 只在距离不超过 `d_min + maxExtraDistanceMeters` 的候选中考虑负载，避免为公平性产生无上限绕行。
- 在合格候选中优先选择当前累计订单较少的骑手；负载相同则按距离，再按 UID。
- 全局负载由单一 Assignment Coordinator 更新，按订单序号处理候选结果，保证同一输入可复现。
- 策略 B 不承诺消灭所有零订单骑手，只要求报告公平性改善及其距离、吞吐和延迟成本。

### 3.3 性能与资源

- 在 2 核 CPU、4GB 内存限制下运行题目给出的四档测试。
- 内存随骑手数量和有界缓冲区增长，不随订单总量无限增长。
- 记录索引构建时间、吞吐量、延迟、最大积压、峰值内存和 GC 情况。
- 明确区分订单到达窗口与最后一笔订单到达后的排空时间。
- 策略 B 使用与策略 A 完全相同的骑手、订单、到达顺序和随机种子进行对照。
- 对两种策略同时记录 Bottom 10、零订单骑手数、订单数方差、变异系数、平均/P95 匹配距离。
- 策略 B 额外报告相对策略 A 的平均距离增长率、吞吐变化和延迟变化。

“最短时间、最少资源”是两个可能相互制约的目标。项目报告以正确性为前提，在 2 核 4GB 硬约束下比较不同实现和参数的完成时间与资源占用。

## 4. 总体技术路线

本方案包含两种匹配策略，实施优先级明确如下：

1. **策略 A：纯就近 Baseline。** 第一版必须优先完成，以最短距离为唯一优化目标，距离相同按 UID。它负责回答题目的核心要求，并建立性能和公平性基准。
2. **策略 B：负载感知扩展。** 仅在策略 A 完成后实施。在有限距离容忍范围内优先低负载骑手，用于研究距离与骑手分配公平性的 trade-off。

策略 A 包含两套匹配器：

1. 暴力扫描匹配器：作为简单、可信的正确性基准。
2. KD-tree 最近邻匹配器：作为大规模测试的主要实现。

策略 A 采用有界 CSP 流水线组织并发：

```text
订单生成器
    │
    ▼
有界批次 Channel
    │
    ├──► 匹配 Worker 1 ──► Worker 1 私有计数
    └──► 匹配 Worker 2 ──► Worker 2 私有计数
                                  │
                                  ▼
                         合并计数并输出后 10 名
```

空间索引构建后只读，由所有 worker 共享。每个 worker 独占自己的计数数组，处理期间不争抢全局锁；所有 worker 退出后再合并结果。

策略 B 复用相同的 Admission Gate、有界队列、KD-tree、Worker Pool、取消和监控能力，但匹配阶段改为 Top-K 查询，并增加一个拥有全局负载状态的 Assignment Coordinator：

```text
订单生成器
    │
    ▼
有界批次 Channel
    │
    ├──► Candidate Worker 1 ──► Top-K CandidateResult
    └──► Candidate Worker 2 ──► Top-K CandidateResult
                                      │
                                      ▼
                         有界结果队列与按序重排
                                      │
                                      ▼
                         Assignment Coordinator
                         距离上限 + 当前全局负载
                                      │
                                      ▼
                         更新计数并输出分配结果
```

Candidate Worker 可以并行查询，但 Coordinator 按订单序号更新负载。策略 B 不使用 worker 私有计数做实时决策，否则不同 worker 看不到一致的当前负载，结果也会随 goroutine 调度顺序变化。

### 4.1 吸收参考文章中的生产级能力

参考文章解决的是“任务以什么顺序、在什么资源约束下执行”，本题还需要解决“订单应匹配哪名骑手”。生产级调度能力位于匹配策略外层，策略 A 和策略 B 大部分共用；两者的核心区别是分配状态的所有权。

| 参考文章中的能力 | 策略 A：纯就近 | 策略 B：负载感知 | 使用阶段 |
| --- | --- | --- | --- |
| Admission Gate | 校验订单 ID、经纬度、配置和输入规模 | 完全复用策略 A，并校验 `topK`、`maxExtraDistanceMeters` 等公平参数 | 步骤一、步骤二；策略 B 在步骤八扩展配置 |
| 有界队列 / MaxInFlight | 通过批次数、batch 大小和 worker 数限制在途订单，不再维护重复的无限任务堆 | 同时限制订单队列、CandidateResult 队列和按序重排窗口 | 步骤六；策略 B 在步骤八增加结果队列 |
| Dispatcher | 将订单批次交给最近邻 worker | 将订单交给 Top-K Candidate Worker，结果交给 Coordinator | 步骤六和步骤八 |
| Worker Pool | 并行执行精确最近邻查询 | 并行执行 Top-K 候选查询，不直接修改全局负载 | 步骤六和步骤八 |
| 批量派发 | 降低逐单 channel 通信和调度开销 | 候选查询可批量，最终分配仍按订单序号提交 | 步骤六和步骤八 |
| 背压 | worker 跟不上时阻塞订单生成器 | 任一订单队列、结果队列或 Coordinator 饱和时逐级传播背压 | 步骤六、步骤八及规定窗口测试 |
| Context 取消 | 通知生成器、worker 和汇总器退出 | 还需通知重排缓冲和 Coordinator 退出 | 步骤六和步骤八的取消测试 |
| Deadline / Timeout | 使用整次运行 context deadline 和阶段耗时监控；纯 CPU 单订单不创建千万个独立 timer | Coordinator 和候选阶段共享运行 deadline，并监控最老未完成 Sequence | 步骤六、步骤八和规定窗口测试 |
| Panic recover | 捕获 worker panic、记录订单和堆栈、标记本次运行失败并取消流水线，不能吞掉订单后继续成功 | Candidate Worker 或 Coordinator panic 同样触发整次运行失败 | 步骤六和步骤八 |
| 优雅停机 | 停止接收、排空订单、等待 worker、合并私有计数 | 停止接收、排空候选结果、完成按序分配、再关闭 Coordinator | 步骤六和步骤八 |
| 指标和结构化日志 | 记录吞吐、延迟、积压、Bottom 10、零订单数、方差、CV 和距离指标 | 使用相同指标，并增加相对策略 A 的距离增长率及 Coordinator 积压 | 步骤四、步骤六、步骤八和性能报告 |
| 幂等和任务 ID | 检测遗漏和重复；作为稳定平局与追踪依据 | 还用于 CandidateResult 的按序重排和去重 | 步骤二、正确性测试和步骤八 |
| 优先级队列和 Aging | 当前不启用，订单按到达顺序处理 | 当前也不启用；负载感知是骑手选择策略，不是订单优先级 | 只有出现 VIP、deadline 或订单饥饿需求后再扩展 |
| 延迟队列、重试退避和死信 | 纯内存匹配不启用 | 纯内存候选与分配同样不启用 | 接入 RabbitMQ、数据库或远程路径服务时使用 |
| 多任务类型资源隔离 | 当前只有最近邻计算任务 | Candidate Worker 与有状态 Coordinator 职责隔离 | 步骤八；未来再隔离路径计算、通知和持久化 |
| 堆数据结构 | 使用容量 10 的最大堆统计 Bottom 10 | Top-K KD-tree 查询使用容量 K 的最大堆维护当前候选 | 步骤四、步骤五和步骤八；它们不是订单优先级队列 |

策略 A 中的 Dispatcher 是逻辑角色：多个 worker 直接竞争消费同一个有界 batch channel 即可完成 fan-out，不为“符合架构图”额外增加无业务价值的 goroutine。只有需要订单优先级、重排或更复杂的派发策略时，才引入独立 Dispatcher。

由此，第一版策略 A 的生产级调度内核是：

```text
Admission Gate
    ↓
有界 FIFO 批次队列
    ↓
Dispatcher + 固定 Worker Pool
    ↓
KD-tree 最近邻匹配
    ↓
私有计数与结果合并
    ↓
指标、取消与优雅停机
```

策略 B 继续使用同一套生产级外壳，但将内部核心替换为：

```text
有界订单队列
    ↓
Top-K Candidate Worker Pool
    ↓
有界 CandidateResult 队列 + 按序重排
    ↓
单一 Assignment Coordinator
    ↓
全局负载计数 + 公平性与距离指标
```

这里的单一 Coordinator 是 CSP 的“状态所有者”：其他 goroutine 通过 channel 发送候选结果，不直接并发修改策略 B 的全局骑手负载。这样减少共享锁，也使相同输入得到可复现结果。

参考文章中的“调度公平性”指订单任务不会因优先级而长期饥饿；策略 B 的“分配公平性”指订单数在骑手之间的分布。两者不是同一问题。本题所有订单默认同优先级，所以 FIFO 加有界背压已经足够；策略 B 不构成启用订单 Priority Queue 或 Aging 的理由。

如果业务后来增加订单优先级，架构演进为：

```text
Admission Gate
    ↓
有界 Priority Queue
    ↓
带 Aging 的 Dispatcher
    ↓
固定 Worker Pool
    ↓
KD-tree 最近邻匹配
```

优先级队列决定“先处理哪笔订单”，KD-tree 决定“订单匹配哪名骑手”，两者不能相互替代。

### 4.2 为什么不能直接照搬参考文章的方法

#### 1. 解决的问题不同

参考文章中的优先级调度器回答“下一项应执行哪个任务”。本题的核心问题是“当前订单应分配给哪个骑手”。骑手相对于订单的距离会随订单位置变化，不存在一个对所有订单都成立的全局骑手优先级。

例如，订单 A 靠近骑手 1，订单 B 靠近骑手 2。将骑手放入一个固定优先级堆，无法同时正确回答这两笔订单的最近骑手。因此本题仍然需要暴力扫描基准和 KD-tree 等空间索引。

#### 2. 优先级堆不会降低最近邻搜索的复杂度

如果只把订单放进文章的 Ready Priority Heap，worker 取出订单后仍逐个遍历所有骑手，那么最大场景仍需要约：

```text
100,000 riders × 10,000,000 orders = 10^12 次距离比较
```

堆只改变订单的执行顺序，没有减少每笔订单搜索骑手的计算量。两个 CPU 核也无法通过增加大量 goroutine 消除这一算法瓶颈。

#### 3. 当前题目没有定义订单优先级

题目没有给出 VIP、订单等级、deadline 或特殊区域等优先级字段。所有订单价值相同时，有界 FIFO channel 的入队和出队成本更低，结果也更容易复现。此时强行使用二叉堆，会为每笔订单增加 `O(log M)` 的维护成本，却不会改善就近匹配结果。

只有业务增加如下规则后，订单优先级队列才有明确语义：

- 即将超过 SLA 的订单优先。
- 等待时间更长的订单通过 Aging 提权。
- VIP 或特殊区域订单优先。
- 重新匹配任务按失败次数和 deadline 调整优先级。

#### 4. 全量 Task 入堆不适合 4GB 下的千万订单

参考文章的通用 `Task` 包含 ID、类型、Payload、多个时间字段、重试状态、租户和追踪信息。如果将千万级订单都构造成任务对象并同时放入堆，任务对象、字符串、指针、堆底层数组和 GC 元数据会占用大量内存。

本题采用流式批处理，只允许有限数量的订单批次在队列中。策略 A 的内存主要取决于骑手索引、worker 私有计数和有界缓冲区；策略 B 额外受全局负载、CandidateResult 队列和按序重排窗口限制。两种策略的内存都不能随订单总数无限增长。

#### 5. 纯内存最近邻失败不适合盲目重试

最近邻查询是确定性计算。同一份非法输入或同一个程序缺陷，在指数退避后重试不会改变结果。延迟队列、重试和死信更适合数据库、RabbitMQ、地图服务等暂时性外部失败。

因此本方案把错误分为：

- 输入或程序错误：立即失败、取消流水线并报告。
- 暂时性外部错误：未来接入外部组件后执行有限重试和退避。
- 超过重试上限的外部任务：进入死信或失败记录，供审计和补偿。

#### 6. 文章示例仍需工程修正和验证

参考文章主要用于解释架构思想，示例不能未经验证直接视为本题的生产实现。需要注意：

- `Config.validate()` 使用值接收者时，函数内部设置的默认值不会回写到原配置。
- 示例声明了 `QueueCapacity`，但展示的 `Submit` 路径没有完整落实容量限制，不能仅靠字段名称证明内存有界。
- 如果堆的 `Less()` 依赖当前时间，且不同任务的 Aging 速度不同，元素相对优先级会随时间改变；已有堆不会仅因时间流逝自动恢复堆序，需要重新评分、定期修复或使用分级队列等策略。
- 单一互斥锁保护 Ready Heap 和 Delay Heap，在高并发提交时可能形成竞争热点，需要通过批量提交、单所有者事件循环或分片降低争用。

这些问题不否定文章的设计方向，而是说明“生产级”必须由明确语义、正确性测试、资源边界和压测数据共同证明。

#### 7. 本方案的取舍

本方案直接吸收文章中适用于当前题目的能力：准入、有界队列、Dispatcher、Worker Pool、背压、取消、异常隔离、指标和优雅停机；使用空间索引补上文章没有解决的供需位置匹配问题。

优先级、Aging、延迟重试和死信作为有明确业务触发条件的扩展点保留，而不是为了展示功能提前增加运行成本。这样既遵循文章的生产化思想，也能在 2 核 4GB 约束下集中解决本题真正的性能瓶颈。

## 5. 实施步骤

### 步骤一：建立独立程序骨架

第一阶段不接入 RabbitMQ、MongoDB 或 Kubernetes，避免外部组件影响算法正确性和性能测量。建议目录结构：

```text
cmd/matcher/
internal/model/
internal/generator/
internal/matcher/bruteforce/
internal/matcher/kdtree/
internal/pipeline/
internal/report/
```

程序配置至少包含：

- 骑手数量。
- 订单数量。
- 订单到达窗口。
- 随机种子。
- 匹配算法。
- worker 数量。
- batch 大小。
- channel 容量。
- 匹配策略，默认且第一版只启用 `nearest`。
- 策略 B 的 `topK`、`maxExtraDistanceMeters`，仅在策略 A 完成后开放。

订单的业务 ID 与流水线顺序号分离：

```go
type Order struct {
    ID               uint64    // 幂等和追踪标识
    Sequence         uint64    // 本次运行内从 0 连续递增的到达顺序
    PlannedArrivalNs int64     // 相对测试起点的计划到达时间
    Pickup           GeoPoint
    Point            Point2D
}
```

策略 A 不依赖 `Sequence` 做选择；策略 B 使用 `Sequence` 对 CandidateResult 保序。生产环境的业务订单 ID 不一定连续，不能承担流水线排序职责。

### 步骤二：实现确定性数据生成器

使用固定随机种子在明确的城市边界框内生成骑手和订单的经纬度，确保测试可复现。默认可以使用现有项目所在的旧金山区域；所有经纬度进入 matcher 后，使用同一个固定原点转换成内部 `Point2D`。

骑手与订单使用彼此独立的随机数流，例如由同一个主种子派生 `riderSeed` 和 `orderSeed`。这样修改骑手生成细节不会意外改变订单序列。策略 A 与策略 B 通过相同配置重新运行确定性订单生成器，不需要把千万订单全部保存到内存，也能重放相同订单、顺序和计划到达时间。

到达模型至少包含：

- `uniform-window`：将指定订单量安排在整个到达窗口内，用于题目四档规模的标准验收。
- `front-loaded-burst`：大部分订单集中在窗口前段，用于观察瞬时积压和背压。
- `unbounded`：不等待计划时间，尽快生成，用于测量纯吞吐上限。

生成器为每笔订单记录计划到达时间。若有界队列已满，发送操作阻塞并产生 admission delay；程序必须报告实际完成注入的时间和最大延迟，不能把背压造成的慢速注入当成已经承受目标流量。

骑手数据只生成一次并保存在内存中。订单采用流式或分批生成，禁止为千万级测试一次性创建千万个包含大量字段的对象。

热路径禁止逐单日志和不必要的堆分配。订单批次、候选缓冲和结果缓冲应复用或预分配；结构化日志只记录运行开始、阶段切换、异常和最终汇总。

测试数据应覆盖：

- 均匀随机分布。
- 热点订单集中在少数区域。
- 骑手稀疏或分布倾斜。
- 重复坐标。
- 城市边界框上的坐标。
- 非法纬度、非法经度和非有限浮点数。
- 相同经纬度经过转换后得到完全相同的 `Point2D`。
- 使用相同投影原点时，生成结果和匹配结果可复现。

### 步骤三：实现串行暴力匹配器

第一版先把订单上车点和骑手位置转换为同一局部平面坐标，再对每笔订单遍历全部骑手，选择投影距离最近者：

```text
distance² = (order.point.x - rider.point.x)²
          + (order.point.y - rider.point.y)²
```

比较内部米制坐标的距离平方即可，不需要调用开平方函数。禁止直接对原始 `latitude/longitude` 计算欧氏距离。策略 A 若距离相同，严格选择 UID 较小的骑手，不读取累计负载。

该版本的复杂度为：

- 单笔订单：`O(N)`。
- 全部订单：`O(N × M)`。

它不用于最大规模测试，而是后续优化版本的标准答案。

先验证以下规模：

```text
10 riders × 100 orders
100 riders × 10,000 orders
```

### 步骤四：实现分配统计和最少 10 名输出

所有订单处理完成后扫描骑手计数，使用容量为 10 的最大堆保留当前订单数最少的 10 名骑手。

比较规则为 `(订单数, UID)`，最终按订单数升序、UID 升序输出。复杂度为 `O(N log 10)`，额外空间为 `O(10)`。

当骑手不足 10 名时输出全部骑手；零订单骑手必须参与统计。

同时以流式或最终扫描方式计算：

- `zeroRiderCount`：订单数为零的骑手数量。
- `min/mean/max orders`：每名骑手订单数的最小值、均值和最大值。
- `variance/stddev`：骑手订单数的总体方差和标准差。
- `CV = stddev / mean`：用于比较不同规模测试的相对离散程度。
- `average/p95 matching distance`：平均和 P95 匹配距离。

匹配时继续使用距离平方进行比较；选中骑手后只对最终距离开平方并累计米数。平均距离用累计距离除以订单数计算；P95 可以使用固定内存直方图或流式分位数估计，不能为了精确分位数保存千万笔距离。

Bottom 10 和零订单数量是观测结果，不作为策略 A 的失败条件。策略 A 的这些指标将成为策略 B 的对照基线。

### 步骤五：实现 KD-tree 最近邻匹配器

根据静态骑手的内部 `Point2D` 构建平衡 KD-tree。每笔订单先执行同样的经纬度投影，再使用精确最近邻搜索，通过子树边界到订单位置的距离下界进行剪枝。KD-tree 中不得混入原始经纬度和投影坐标。

需要特别验证：

- KD-tree 结果与暴力匹配器完全相同。
- 剪枝逻辑不会漏掉等距离但 UID 更小的骑手。
- 重复坐标和退化分布不会产生错误结果。
- 暴力版本和 KD-tree 使用同一个投影器实例、原点和距离函数。

KD-tree 在低维、分布合理的数据上通常能够显著减少比较次数，但精确查询的最坏情况仍可能退化为 `O(N)`。报告中应陈述实际测试结果，不预先承诺固定复杂度或吞吐量。

### 步骤六：为策略 A 加入 CSP 并发流水线

正确性得到验证后，再加入并发。初始参数建议：

```text
GOMAXPROCS = 2
workers     = 2
batch size  = 256 或 512
channel     = 8～32 个 batch
```

关键原则：

- 不为每笔订单启动一个 goroutine。
- 订单生成器负责关闭输入 channel。
- 多个 worker 从同一个输入 channel 获取不同批次，实现 fan-out。
- 每个 worker 使用自己的 `[]uint64` 骑手计数数组。
- worker 完成后通过 channel 交出计数数组，之后不再修改。
- 汇总协程等待全部 worker 完成后合并计数。
- 通过 `context.Context` 或关闭信号传播取消，避免 goroutine 泄漏。
- channel 必须有界，使下游处理变慢时能够形成背压。
- 策略 A 不读取全局实时负载，因此 worker 私有计数不会改变最近邻选择结果。
- 队列满时阻塞生产者，不能丢弃合法订单；如果 context 截止导致未完成，则整次测试失败并报告已生成、已入队、已完成和未完成数量。
- worker panic 必须 recover、记录订单 ID/Sequence 和堆栈，然后取消整条流水线；不能吞掉该订单后继续把运行标记为成功。

批次通过 slice 传递时不会复制底层数组。生产者必须在消费者处理完成前停止复用对应缓冲区，或者使用有界缓冲池明确转移所有权。

完成并发版本后，用相同输入比较：

```text
串行 KD-tree 计数 == 并发 KD-tree 计数
```

正常结束的关闭顺序为：停止生成并关闭订单输入、worker 排空输入后退出、等待全部 worker、合并计数、输出报告。取消或致命错误路径不承诺排空，但所有 channel 发送和接收都必须监听 context，保证 goroutine 能退出，并明确报告未完成订单数。

### 步骤七：验证策略 A 的内存边界

设骑手数为 `N`，worker 数为 `W`，队列中最多存在 `Q` 个批次，每批包含 `B` 笔订单，则核心内存量级为：

```text
O(N + WN + QB)
```

其中：

- `O(N)`：骑手和空间索引。
- `O(WN)`：worker 私有计数数组。
- `O(QB)`：有界订单缓冲。

10 万骑手、2 个 worker 时，仅两个 `uint64` 计数数组约占：

```text
100,000 × 2 × 8 bytes = 1.6 MB
```

该数值不包含空间索引、订单缓冲、goroutine 栈、运行时和 GC 开销；真实峰值内存必须通过测试获得。

完成步骤七以及策略 A 的四档规模验收后，第一版核心目标即完成。策略 B 属于后续扩展，不得在此之前引入策略 A 的主处理链路。

### 步骤八：实现策略 B 的负载感知扩展

策略 B 复用策略 A 的数据生成器、投影器、KD-tree、Admission Gate、有界队列、取消、监控和资源限制测试。主要变化如下：

1. KD-tree 从查询单个最近骑手扩展为查询 Top-K 最近候选；候选按 `(distanceSquared, UID)` 稳定排序，确保相同距离时的候选集合可复现。
2. Candidate Worker 只负责无状态的 Top-K 查询，并返回订单 ID、Sequence、候选 UID 和距离。
3. CandidateResult 进入有界结果队列；乱序完成的结果在有界窗口内按 Sequence 重排。
4. 单一 Assignment Coordinator 按连续 Sequence 读取结果并独占全局 `[]uint64` 骑手负载。
5. 先取得最近距离 `d_min`，只保留 `distance <= d_min + maxExtraDistanceMeters` 的候选。
6. 在合格候选中选择当前累计订单最少者；负载相同则选择距离更近者，仍相同则选择 UID 更小者。
7. Coordinator 完成选择后立即更新该骑手的全局订单数。

`maxExtraDistanceMeters` 是公平性与距离成本的显式控制参数：

- `0` 表示不允许额外距离，结果退化为策略 A 的最近距离集合。
- 参数越大，越可能选择低负载但更远的骑手。
- 候选始终受距离上限和 Top-K 限制，不能为了消灭零订单骑手无限扩大配送距离。

策略 B 不沿用策略 A 的 worker 私有计数，因为公平选择必须读取一致的当前全局负载。若使用多个 worker 直接对原子计数做“读负载—选择—增加”，结果会受到 goroutine 时序影响，难以保证相同输入可复现。

策略 B 的内存除复用策略 A 的 `O(N + QB)` 外，还包括：

```text
O(N)  全局骑手负载
O(RK) 有界 CandidateResult 与重排窗口
```

其中 `R` 是重排窗口内最多保留的订单结果数，`K` 是每笔订单的候选数。`R` 和 `K` 都必须有明确上限。

## 6. 测试方案

### 6.1 单元与正确性测试

至少覆盖：

- 无骑手时返回明确错误。
- 只有一名骑手。
- 订单与骑手坐标完全相同。
- 多名骑手距离相同。
- 多名骑手坐标相同。
- 经纬度范围校验正确。
- 已知经纬度样例投影后的方向和量级正确。
- 原始经纬度模型与内部 `Point2D` 不发生经纬度顺序颠倒。
- OSRM `[longitude, latitude]` 到项目 `Latitude/Longitude` 的边界转换正确。
- 大量骑手获得零笔订单。
- 固定种子结果可复现。
- KD-tree 与暴力算法逐单对照。
- 策略 A 的串行结果与并发结果一致。
- 最少 10 名的顺序和数量正确。
- 取消后所有 goroutine 能够退出。
- 策略 B 的 Top-K 候选与暴力 Top-K 结果一致。
- 策略 B 不会选择超过 `d_min + maxExtraDistanceMeters` 的骑手。
- 策略 B 的 CandidateResult 即使乱序到达，Coordinator 仍按订单序号产生确定结果。
- 策略 B 在相同种子、参数和输入下结果可复现。

运行 Go race detector 检查并发数据竞争。

### 6.2 防止遗漏和重复

`所有骑手订单数之和 == M` 是必要条件，但不能单独证明每笔订单恰好处理一次。

正常完成时必须满足：

```text
generated == admitted == completed == requestedOrders
sum(riderOrderCounts) == completed
```

测试模式根据连续 Sequence 使用位图记录处理情况，检查每个 Sequence 是否恰好出现一次。1,000 万个位约占 1.25MB，适合在 4GB 限制下作为测试辅助数据。

并发 worker 不能无保护地修改同一个位图字。可以让每个 worker 使用私有位图，结束后按位合并并检测重复；也可以使用正确的原子位操作。第一版优先采用 worker 私有位图，与私有骑手计数的所有权模型一致。该位图只在正确性测试中启用，正式性能测试关闭，避免污染性能数据。

### 6.3 最大吞吐测试

不主动限制生成速度，尽快生成订单，测量纯计算上限：

- 总处理时间。
- 每秒处理订单数。
- 索引构建时间。
- CPU 使用率。
- 峰值内存。
- 分配次数、GC 次数和 GC 时间。

### 6.4 规定窗口测试

按照题目要求的时间窗口产生订单，记录：

- 计划生成数量与实际生成数量。
- 实际订单到达速率。
- 最大队列积压。
- 最后一笔订单到达后的排空时间。
- `planned arrival → admitted` 的 admission delay P50/P95/P99。
- `admitted → completed` 的排队与匹配延迟 P50/P95/P99。
- `planned arrival → completed` 的端到端延迟 P50/P95/P99。
- 是否出现持续内存增长。

生产者被背压阻塞后导致的低输入速度，不能被误报为系统已承受目标突发量。如果订单未能在规定窗口内完成注入，报告中必须明确说明。

延迟分位数使用固定内存直方图或流式估计，不能保存千万条延迟。所有时长使用 Go 单调时钟计算，墙上时间只用于日志展示。

开发阶段可以使用时间缩放快速验证流量模型，最终报告应执行真实时间窗口测试。

### 6.5 资源限制测试

最终测试使用真实的 2 核 CPU 和 4GB 内存限制，并设置 `GOMAXPROCS=2`。`GOMAXPROCS` 只控制 Go 代码并行度，不能替代操作系统或容器的 CPU、内存硬限制。

容器或操作系统负责 4GB 硬上限；可以把 `GOMEMLIMIT` 设置为低于硬上限的值，为 goroutine 栈、非 Go 内存、profile 和运行时保留余量。报告必须记录实际限制和 Go 运行时设置，不能只写理论配置。

按照以下顺序逐级测试：

1. 100 名骑手、10,000 笔订单。
2. 1,000 名骑手、100,000 笔订单。
3. 10,000 名骑手、1,000,000 笔订单。
4. 100,000 名骑手、10,000,000 笔订单。

每一档通过正确性检查后再进入下一档。

策略 A 必须独立完成以上四档测试。策略 B 使用与策略 A 相同的输入数据执行对照，不得用重新生成的数据比较公平性和距离。

### 6.6 策略 A 与策略 B 对照实验

第一轮先运行策略 A 并固化结果，再在相同骑手、订单、到达顺序、随机种子、投影参数和资源限制下运行策略 B。

策略 B 至少测试：

```text
topK = 4, 8, 16
maxExtraDistanceMeters = 0, 100, 300, 500
```

参数范围可以根据城市尺度和首次结果调整，但报告必须保留策略 A，并明确每组策略 B 参数。比较指标包括：

- Bottom 10 及各自订单数。
- 零订单骑手数量。
- 骑手订单数方差、标准差和 CV。
- 平均、P95 和最大匹配距离。
- 相对策略 A 的平均距离增长率。
- 吞吐量、P95/P99 匹配延迟和排空时间。
- CPU、峰值内存和 Coordinator 最大积压。

公平性改善不能只展示订单方差下降，还必须同时展示距离、延迟和吞吐成本。

## 7. 性能报告格式

每组测试记录以下内容：

| 分类 | 指标 |
| --- | --- |
| 输入 | 骑手数、订单数、到达窗口、随机种子、数据分布 |
| 配置 | 策略、算法、worker 数、batch 大小、channel 容量、GOMAXPROCS；策略 B 额外记录 Top-K、额外距离上限和重排窗口 |
| 正确性 | 成功分配数、遗漏数、重复数、计数总和 |
| 时间 | 索引构建、生成、匹配、总耗时、排空耗时 |
| 性能 | 吞吐量、P50/P95/P99 延迟、最大积压 |
| 资源 | 平均/峰值 CPU、峰值内存、分配量、GC 次数与耗时 |
| 分配结果 | Bottom 10、零订单骑手数、min/mean/max、方差、标准差和 CV |
| 距离结果 | 平均/P95/最大匹配距离；策略 B 相对策略 A 的距离增长率 |
| 策略 B 状态 | CandidateResult 队列与重排窗口最大积压、Coordinator 处理速率 |

同时比较：

- 暴力扫描与 KD-tree。
- 1、2、4 个 worker。
- 不同 batch 大小和 channel 容量。
- 策略 A 与不同 `topK/maxExtraDistanceMeters` 的策略 B。

不能假设 worker 越多性能越高。在 2 核环境中，生成器、汇总器和 Go runtime 同样需要 CPU，应以基准测试结果确定参数。

## 9. 与现有项目的关系

现有 driver service 的匹配过程是先按车型筛选，再随机选择司机。本题实现完成后，可以把匹配内核作为后续演进方案：

1. Trip Service 在匹配事件中提供明确的订单 `pickupLocation` 经纬度。
2. Driver Service 校验经纬度，并使用固定投影器转换为内部 `Point2D`。
3. 先按车型、服务状态、位置时效和容量筛选候选骑手。
4. 使用投影后的骑手坐标建立或更新空间索引。
5. 使用订单上车点的投影坐标执行最近邻搜索。
6. 将选择结果通过现有消息链路发送给目标骑手。

接入顺序仍然先采用策略 A，替换当前随机选择并验证线上指标。只有业务明确接受额外距离换取骑手分配公平性后，才启用策略 B，并通过配置控制 `topK` 和 `maxExtraDistanceMeters`。策略切换和参数必须进入指标标签，保证两种策略的结果可以对照和回滚。

本次程序设计测试优先证明单机匹配内核的正确性、吞吐能力和资源边界，不直接改造已有微服务。

接入前必须完成两个坐标链路修正：

- 统一 OSRM GeoJSON 的 `[longitude, latitude]` 与项目对象的 `Latitude/Longitude` 映射。
- 实现当前尚未处理的 `DriverCmdLocation`，并定义骑手位置的更新时间、过期规则和索引更新策略。

对外协议继续表达经纬度，`Point2D` 只属于 matcher 内部实现，不能通过现有 API 冒充真实经纬度返回给前端。

## 10. 面试讨论重点

需要能够清楚回答：

- 为什么暴力版本仍有价值：它提供简单可信的正确性基准。
- 为什么不能只增加 goroutine：最大场景下暴力算法需要约 `10^12` 次距离比较，核心问题首先是算法复杂度。
- 为什么选择 KD-tree：骑手位置静态、坐标低维，适合建立只读空间索引。
- 为什么不能直接对经纬度做二维欧氏距离：经纬度不是等比例平面坐标，经度尺度随纬度变化；本方案先统一投影到城市局部米制坐标。
- 为什么不修改现有经纬度协议：经纬度是系统边界和地图服务的正确业务表达，投影坐标只是匹配器内部优化表示。
- 如何获得订单匹配位置：使用明确的 `pickupLocation`，不依赖路线数组首元素推断核心业务字段。
- 如果“最近”改成道路 ETA 怎么办：先用空间索引召回少量候选，再由路网服务计算候选 ETA。
- 为什么 channel 有界：建立背压并限制在途订单占用的内存。
- 为什么策略 A 不用全局原子计数：纯就近选择不依赖实时负载，worker 私有计数可以避免热点争用，最终合并成本可控。
- 为什么策略 B 不能继续使用 worker 私有计数：公平选择必须看到一致的当前全局负载，因此由单一 Coordinator 作为状态所有者。
- 为什么策略 B 不直接让多个 worker 更新原子计数：复合的“读取负载—比较候选—选择—增加”不是单次原子操作，结果会受并发时序影响。
- 为什么先交付策略 A：它直接满足题意、提供正确性基准和性能基线；没有策略 A 就无法量化策略 B 的公平性收益和距离成本。
- 如何评价分配公平性：Bottom 10 只观察尾部，还要结合零订单人数、方差、CV 和订单空间分布。
- 如何量化策略 B 的 trade-off：在完全相同输入下，同时比较公平指标、平均/P95 距离、吞吐和延迟。
- 为什么不为每笔订单创建 goroutine：千万级 goroutine 会增加内存和调度成本。
- 如何证明没有漏单或重复：计数守恒加连续 Sequence 位图检查，业务订单 ID 只用于幂等和追踪。
- 如何保证可复现：固定随机种子和稳定的距离平局规则。
- 为什么需要区分到达窗口和处理耗时：二者分别代表入口负载和系统服务能力。
- 如果骑手位置动态变化怎么办：需要支持索引更新、快照或分片，读写一致性也会成为新问题。
- 如果骑手有接单容量怎么办：匹配和容量占用必须成为协调状态变更，需要单一状态所有者、分片或原子预占，不能再只依赖 worker 私有计数。
- 如果要求公平怎么办：严格最近与负载均衡是不同目标；策略 B 通过 Top-K、最大额外距离和实时负载规则限定取舍，并用对照指标说明成本。

## 11. 第一个编码里程碑

第一阶段编码目标限定为：

> 优先完成策略 A：创建独立 matcher，完成可复现的城市范围经纬度生成器、统一的经纬度到 `Point2D` 投影、串行暴力最近邻匹配和包含零订单骑手的 Bottom 10 统计；距离相同严格按 UID，不读取实时负载，不接入现有微服务，不加入并发。

完成后必须先获得策略 A 的小规模正确性结果，再依次实现策略 A 的 KD-tree 和 CSP 并发流水线。策略 A 完成四档测试和性能报告之前，不开始策略 B；策略 B 是可选的第二阶段公平性实验。

## 12. 实现准备结论

在本文冻结的假设下，第一版没有仍需等待面试官回答的阻塞问题，可以进入实现阶段。若后续得到与本文不同的明确要求，应先更新假设和验收标准，再修改代码。

策略 A 的 Definition of Done：

- 配置校验、确定性骑手/订单生成器和固定局部投影器完成。
- 串行暴力最近邻、UID 平局规则和包含零订单骑手的 Bottom 10 完成。
- KD-tree 与暴力版本在小规模和随机样例上逐单一致。
- 有界 CSP 流水线、worker 私有计数、取消、fatal panic 传播和正常优雅停机完成。
- 正常运行满足生成、准入、完成和计数守恒；race detector 与必要的正确性测试通过。
- 四档规模按顺序运行，并输出吞吐、三段延迟、积压、CPU、峰值内存、GC、分配公平性和匹配距离指标。
- 在真实 2 核、4GB 限制下记录可复现的运行命令、配置、随机种子和结果。

第一版明确不包含：

- 策略 B 的 Top-K 负载感知分配。
- 对现有微服务、protobuf、RabbitMQ 或数据库的改造。
- 动态骑手位置和空间索引在线更新。
- 订单 Priority Queue、Aging、延迟队列、重试和死信。
- 道路 ETA 匹配或外部 OSRM 调用。

这些能力已有明确扩展位置，但不会进入策略 A 的热路径或延误第一版交付。
